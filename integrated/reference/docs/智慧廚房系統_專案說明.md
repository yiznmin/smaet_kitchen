# 智慧廚房影像分析系統 — 專案說明（給 Claude Code 協作用）

> 本文件供 Claude Code 理解整個專案的目標、架構與各模組職責，作為開發協作的共同基準。
> 文件分三部分：(A) 專案總覽與架構、(B) 九大模組逐一說明、(C) 資料集與驗證策略。

---

## A. 專案總覽

### A.1 一句話定位

一套導入餐飲廚房現場的電腦視覺系統，用多顆攝影機即時偵測人員、食材、器具，跨鏡頭維持廚師身份，並以可解釋的規則邏輯產出食安相關事件（如生熟交叉污染、未洗手、停留超時），供事後追溯與調查。

### A.2 兩種部署架構（重要）

本專案存在兩種架構版本，開發時務必先確認目前針對哪一種，因為模組邊界與通訊方式不同：

| 架構 | 說明 | 模組數 | 是否用 LLM/VLM |
|---|---|---|---|
| **集中式單主機**（計畫書採用） | 攝影機只負責 RTSP 串流，所有運算集中在一台 GPU 主機 | 整併為 4 大模組 | 否，純規則邏輯 |
| **邊緣—中央分散式**（完整架構規劃） | 每鏡頭一個邊緣節點，中央只做協調與儲存 | 9 個模組 M1–M9 | 視版本，可含 VLM |

> **目前計畫書版本為「集中式」，且明確不引入 LLM/VLM，所有事件判斷採可驗證、可解釋的規則邏輯。**
> 下方模組說明以「完整 9 模組」為主軸條列（便於開發拆解），並標注其在集中式架構中的歸併位置。

### A.3 核心設計原則

- **影像不必要時不離開來源**：原始影像在本地/主機處理，跨模組只傳結構化資料（事件、特徵向量、查詢）。
- **事件驅動，而非每幀通訊**：大部分時間各模組獨立運作，只在關鍵時刻（新身份、跨鏡頭、離開、事件）才交換訊息。
- **重運算放前端、輕協調放後端**：影像處理與 GPU 推論在前端，全域狀態維護與儲存查詢在後端。
- **可解釋優先**：事件判斷用規則引擎與狀態機，確保結果可人工驗證、可重現、可審計。
- **不綁定特定模型版本**：各模組設計「版本評估 → 選型 → 驗證」流程，依實測決定最終採用版本。

### A.4 技術棧

| 領域 | 技術 |
|---|---|
| 物件偵測 | RF-DETR（選定，準確優先；Apache-2.0）。註：YOLOv8/v11 為 AGPL，不出貨 |
| 物件追蹤 | ByteTrack（主力）、BoT-SORT（遮擋備選） |
| 重識別 Re-ID | OSNet（外觀特徵）、InsightFace（人臉） |
| 精細分割 | SAM 2 |
| 語意描述（僅分散式版） | Qwen2-VL |
| 資料庫 | PostgreSQL（時序事件）、Neo4j（實體關聯圖） |
| 後端 / 前端 | FastAPI、Vue 3 |
| 影像 I/O | OpenCV / GStreamer |
| 通訊（分散式版） | MQTT、gRPC、HTTP REST |

## B. 九大模組說明

> 每個模組統一以「功能 / 輸入 / 輸出 / 開發目標 / 驗收標準」五段呈現。

### M1　影像擷取模組

- **部署**：邊緣節點（集中式中為主機端擷取層）
- **功能**：從攝影機（IP Camera RTSP / USB）即時取得影像串流、解碼為標準 BGR numpy array、控制取樣頻率、處理斷線重連與來源異常容錯。
- **輸入**：攝影機 RTSP / USB 串流；設定參數（解析度、FPS、cam_id）。
- **輸出**：影格 frame、時間戳 timestamp、影格序號 frame_id、鏡頭編號 cam_id。
- **開發目標**：穩定、可容錯地把多路串流轉成下游可用的標準影格流，長時間運作不掉線、不漏幀累積。
- **驗收標準**：接入真實攝影機可持續取流；模擬斷線後能自動重連；多路同時擷取時幀率穩定。

### M2　動態偵測模組

- **部署**：邊緣節點
- **功能**：用背景差分（cv2.absdiff）判斷畫面是否有變動，過濾靜止影格，當無人活動時讓 M3 偵測器進入低耗模式。是 GPU 算力的「省電開關」。詳細的雙分支重構（含小目標專線）見 [M2_雙分支重構設計.md](../docs/M2_雙分支重構設計.md)。
- **輸入**：M1 影格、前一張參考影格。
- **輸出**：has_motion 布林值、動態區域 bbox（可選，供 ROI 加速）、通過篩選的影格。
- **開發目標**：以極低 CPU 成本正確區分「有動 / 無動」，顯著降低 M3 的無效推論次數。
- **驗收標準**：空檔畫面正確判為無動態並不下傳；有人活動時不漏觸發；可量測出對 GPU 負載的實際節省比例。

### M3　物件偵測模組（RF-DETR）

> 模型定案：採 **RF-DETR**（準確優先，小物件最強；Apache-2.0）。選型理由見 [模型選型評估.md](../docs/模型選型評估.md) 與 [M2_雙分支重構設計.md](../docs/M2_雙分支重構設計.md)。本案**注重準確不注重速度**，故捨速度冠軍 D-FINE-N，改採 RF-DETR。

- **部署**：邊緣節點（集中式中為主機端批次推論）
- **功能**：對單張影格偵測所有目標（人、食材、器具），輸出每個物件的 bbox、類別、信心分數。無跨幀記憶，純粹「這一幀有什麼」。
- **輸入**：M2 篩選後影格、RF-DETR 權重檔（ONNX）、偵測類別清單（person, chicken, knife, cutting_board…）、信心閾值、批次大小。
- **輸出**：Detection 清單，每筆含 bbox [x1,y1,x2,y2]、class、confidence、frame_id、timestamp、cam_id。
- **開發目標**：選出在目標主機上對廚房類別（尤其刀具等小物件）**準確度足夠**的 RF-DETR 變體與設定（準確優先取 small/medium）；支援多鏡頭批次推論以提高 GPU 使用率。
- **驗收標準**：
  - 速度：在目標主機上量出各版本/解析度/批次的延遲、FPS、GPU 記憶體，產出選型表。
  - 準確度：在標註廚房資料集上量各類別 precision / recall / mAP。
  - 多路：以批次推論驗證可支援的鏡頭數與端到端延遲。

### M4　物件追蹤模組（ByteTrack）★ 關鍵橋樑

- **部署**：邊緣節點
- **功能**：把 M3 每幀獨立的偵測串成有 ID 的物件軌跡（卡爾曼濾波預測 + IoU + 匈牙利配對），自動分配 track_id、維持跨幀一致性、支援短暫遮擋。是「單幀偵測」與「時間維度事件判斷」之間不可省略的橋樑。
- **輸入**：M3 Detection 清單（無 ID）、前幾幀追蹤狀態。
- **輸出**：Track 清單（track_id、bbox、class、軌跡歷史、狀態 active/lost/removed）、新出現 track 事件（觸發 M5 抽特徵）、消失 track 事件（觸發通知中央）。
- **開發目標**：在遮擋頻繁、人員密集下維持穩定 track_id、低 ID switch；純 CPU 即時運行。
- **驗收標準**：單鏡頭長時段影片下軌跡連續、ID switch 次數低；物件短暫遮擋（5–10 幀）後能維持原 ID；每幀處理 < 5ms。
- **⚠ 開發備註**：M3 偵測器（RF-DETR）與 SAM 2 都是單張影像處理器、不知道跨幀是否同一物件；SAM 2 的影片追蹤需人工指定 prompt 且只追特定物件，**不能取代** ByteTrack 的「自動為所有偵測分配並維持 ID」。此模組不可省略。

### M5　廚師身份管理模組（Re-ID）

- **部署**：邊緣抽特徵 + 中央比對（混合）；集中式中為主機內行程呼叫
- **功能**：把本地 track_id 綁定到全域 chef_id。入場用 InsightFace 人臉辨識確認身份；用 OSNet 抽 512 維外觀特徵作跨鏡頭比對依據；中央維護「活躍清單」記錄當下所有廚師特徵與狀態；廚師跨鏡頭時以餘弦相似度比對 recently_disappeared 廚師維持身份連續性。
- **輸入**：（邊緣）新出現 track 的人物 crop、入場人臉影像；（中央）特徵向量 + track_id、活躍清單當前狀態。
- **輸出**：（邊緣）512 維特徵向量、Re-ID 查詢請求；（中央）比對結果 {match, confidence}、更新後活躍清單、chef_id ↔ track_id 綁定關係。
- **開發目標**：在多鏡頭、不重疊視角、跨時間情境下穩定維持人員全域身份；活躍清單記憶體可控、有清理機制。
- **驗收標準**：廚師從 cam_01 走到 cam_02 後 chef_id 不中斷；多人情境下身份不互相混淆；連續運作下活躍清單記憶體不無限成長。

### M6　事件判斷模組（第一層 / 粗篩選）

- **部署**：邊緣節點
- **功能**：依 M4 軌跡、M5 身份、M3 物件位置與預定義 zone，用規則引擎 + 有限狀態機產出「粗事件」（進入/離開 zone、接觸物件、停留超時）。同時是高成本 M7 的「守門員」，只在符合規則時才觸發精細分析。
- **輸入**：M4 Track 清單、M5 chef_id、zone 配置（生肉區、熟食區、洗手台…）、事件規則設定（接觸距離、停留時間閾值）。
- **輸出**：粗事件（含 chef_id、zone/object、time、duration）、觸發 M7 的訊號（指定時間區間、鏡頭、物件）。
- **開發目標**：以低 CPU 成本即時產出可解釋、可審計的粗事件；規則閾值以設定檔管理、可依場域調整、不需重訓模型。
- **驗收標準**：事件正確率（對照人工檢視清單算 precision/recall）達標；M7 觸發不漏觸發、不過度觸發；設定檔調整可重現。
- **規則分類**：(a) 空間規則（中心點是否進入區域多邊形、bbox 間距是否小於接觸閾值）；(b) 時序規則（持續 > N 秒、T 秒內切換 K 次）；(c) 組合規則（複雜情境串接）。

### M7　精細分析模組（第二層 / 細篩選）

- **部署**：邊緣節點
- **功能**：在 M6 觸發時對指定物件做精確分割（SAM 2 產生像素級 mask），依物件重疊關係、相對位置與時序變化判斷更精細的事件（如「持刀切割生肉」「生肉容器置於熟食檯面」）。
  - **集中式版**：不使用 VLM/LLM，細事件以幾何重疊（IoU、IoA）、相對位置與規則邏輯判斷。
  - **分散式版**：可額外用 Qwen2-VL 產生語意描述文字。
- **輸入**：M6 觸發訊號、該區間影片片段/關鍵影格、M3 bbox 作 SAM 2 prompt、重疊判斷規則。
- **輸出**：物件 mask 序列、細事件（chef_id、object、重疊關係、time_range、mask_path）。
- **開發目標**：只在必要時觸發（高成本，不每幀跑）；以非同步佇列排程，優先讓即時偵測/追蹤取得 GPU。
- **驗收標準**：分割 IoU 與細事件正確率達標；重疊判斷在不同視角/遮擋下穩定；不影響即時模組延遲。

### M8　儲存模組

- **部署**：中央伺服器
- **功能**：接收所有事件寫入資料庫。PostgreSQL 存結構化時序事件、Neo4j 維護實體關聯圖（廚師、物件、區域、事件的關係）、管理 mask 檔與影片片段引用。提供統一資料層給 M9。
- **輸入**：M5 身份事件、M6 粗事件、M7 細事件 + mask 路徑、本地影片片段引用。
- **輸出**：寫入確認、對 M9 的查詢介面（SQL / Cypher）、事件紀錄與關聯圖。
- **開發目標**：兩類資料結構並存 — (a) 時序事件表（按時間/人員/類型查詢）、(b) 實體關聯表（圖式追溯）；原始影片留本地、DB 存路徑引用以兼顧成本與效率。
- **驗收標準**：寫入效能、查詢回應時間、資料完整性達標；關聯圖更新正確。

### M9　查詢與前端模組

- **部署**：中央伺服器
- **功能**：FastAPI 後端供查詢、Vue 3 前端供瀏覽事件/時間軸/廚師活動；支援交叉污染追溯、廚師活動歷史、特定時段查詢；前端疊加 mask 視覺化。系統唯一對外入口。
- **輸入**：使用者 HTTP 請求（時間、chef_id、事件類型）、M8 查詢結果、影片/mask 存取請求。
- **輸出**：JSON API 回應、前端網頁（時間軸、播放器、關聯圖）、含 mask 疊加的影片串流、報表（每日統計、異常清單）。
- **開發目標**：提供直覺的調查查詢介面，使用者不需接觸邊緣或資料庫。
- **驗收標準**：能查「chef_003 今日接觸物件」與交叉污染路徑；Cypher 查詢效能達標；前端時間軸與 mask 疊加正確顯示。

## C. 資料集與驗證策略

> 關鍵原則：**沒有任何單一公開資料集能涵蓋整個專案。**
> 公開資料集驗證「演算法本身對不對」，自錄資料驗證「在本廚房能不能用」，兩者缺一不可。

### C.1 各模組對應的資料來源

| 模組 | 驗證目標 | 資料來源 | 需要的標註 |
|---|---|---|---|
| M3 | 偵測**速度/資源** | EPFL-Smart-Kitchen（exocentric 固定視角） | 不需要 |
| M3 | 偵測**準確度** | Roboflow 廚房資料集 + 自標場域畫面 | 物件 bbox |
| M4 | 單鏡頭追蹤正確性 | DukeMTMC / MTA / MOT17 | track ID |
| M5 | 跨鏡頭 Re-ID 正確性 | MARS / CUHK-SYSU / DukeMTMC-reID | 人物 ID |
| 全系統 | 整合 + 部署驗證 | **自錄資料** | chef_id + 鏡頭 + 時間 |

### C.2 EPFL-Smart-Kitchen 的能與不能

來源：`https://github.com/amathislab/EPFL-Smart-Kitchen`（多視角烹飪行為資料集，含 exocentric 固定相機與 egocentric 頭戴視角）。
本專案**只用 exocentric（固定相機）部分**，egocentric 與本部署情境不符，不使用。

| 用途 | 可否 | 條件 |
|---|---|---|
| M3 速度/資源評估 | ✅ | 無條件，最穩 |
| M3 準確度評估 | ❌ | 無物件 bbox 標註 |
| M2 動態偵測驗證 | ✅ | 連續影片適合測觸發與節省比例 |
| M1 流程跑通 | 🟡 | 僅測讀檔解碼；RTSP 串流/斷線重連需真攝影機 |
| M4 單鏡頭追蹤 | 🟡 | **需畫面同時有多人才有意義（待確認）** |
| M5 跨鏡頭 Re-ID | ❌ | 其為重疊同步多視角，與「跨區跨時重識別」情境不符 |
| 管線壓力測試 / demo | ✅ | 定性即可 |

### C.3 M3 速度評估具體在測什麼

用 EPFL exocentric 影片，回答核心問題：**「哪個可商用模型/設定能在目標主機上即時處理多路鏡頭？」**（最終選定 RF-DETR，準確優先）

測試矩陣：
- 模型：可商用 Apache-2.0 候選（RF-DETR / D-FINE / RT-DETRv2…），各取代表變體
- 輸入解析度：640、1280
- 批次大小：1、4、8（模擬多鏡頭同時進來）

每個組合記錄：

| 欄位 | 說明 |
|---|---|
| 模型版本 / 尺寸 | rfdetr-s、rfdetr-m、dfine-n… |
| 輸入解析度 | 640 / 1280 |
| 批次大小 | 1 / 4 / 8 |
| 單張推論延遲 (ms) | 平均 + p95 |
| 吞吐率 (FPS) | 批次下有效幀率 |
| GPU 記憶體峰值 (MB) | |
| 可支援鏡頭數估算 | 依 FPS 與目標幀率推算 |

附帶可測：有無 M2 預過濾對 GPU 負載的節省比例。

> **速度評估不需要任何標註**，純計時計量即可；這正是 EPFL（有畫面、無物件框）能做的那一半。
> 準確度評估需要 bbox ground truth，改用 C.1 中的廚房標註資料集。

### C.4 待確認事項（影響測試規劃，需親自下載驗證）

1. EPFL exocentric 影片的**實際解析度與幀率** — 決定 1280 / 高幀率測試是否有意義。
2. exocentric 畫面**同時出現幾位受試者** — 決定 M4 單鏡頭追蹤能否用此資料驗證。
3. 各資料集（EPFL/Zenodo、Roboflow、DukeMTMC 等）的**授權條款** — 委託研究使用前須逐一確認；DukeMTMC 曾因隱私爭議下架，須查現況。
4. 速度測試務必在**實際部署的目標主機**上跑，他機數據不可直接套用。

### C.5 自錄整合驗證資料規格（無可取代）

用於 M5 與全系統最終驗證，需自行錄製：
- 多位人員（建議 2–3 人，外觀有區別）
- 在不同工作站/鏡頭間來回走動
- 包含「離開某鏡頭後隔一段時間再出現」的情境
- 人工標註：chef_id、出現於哪台鏡頭、起訖時間

## D. 開發優先順序建議（Phase）
