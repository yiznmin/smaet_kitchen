## 1. 為什麼跑這一輪

- 平面圖幾何接入(`docs/M5_平面圖幾何接入_預先登記_20261013.md`)只測了單人 L3 的 17 段與多人 7 序列全長,
  而且走的是 `scripts/m5_track_video.py`,不是整合管線。
- 使用者要的是:**接進 `integrated/run_pipeline.py`,在六個子集上測**。
- 六個子集 = 資料集根目錄的六份 CSV,與外部交接包 `CHIRLA_L3_handover` 的六份清單逐檔雜湊相同,
  所以測的是同一批片段。交接包的數字用標註軌跡當單鏡頭追蹤;這裡用真實的 M3 偵測 + M4 追蹤。

## 3. 四組設定(`integrated/pipeline_config.yaml` 的 profile)

| profile | M4 | M5 embedder | M5 拓撲 |
|---|---|---|---|
| `delivery` | C-BIoU | 無 | 原拓撲 |
| `single_person` | 外觀關聯 DINOv2 w = 0.7 | dinov2 | 修正拓撲 |
| `plan_strict`(P1) | 同 single_person | dinov2 | 修正拓撲 + 平面圖位置證據(全域 σ,自己要過門檻) |
| `plan_share`(Q2) | 同 single_person | dinov2 | 修正拓撲 + 平面圖位置證據(逐鏡頭對 σ,依位置分配) |

- 共用:COCO 預訓 RF-DETR nano 的偵測快取、thr 0.10、stride 5、TTL 600 迴圈、M2 閘門關閉。
- **逐片段獨立推論**:每段一個新 process,只給該段指名的鏡頭與幀範圍,狀態從零開始。
- 指令:`python integrated/run_pipeline.py --profile <profile> --seq <序列> --videos … --cameras … --det-cache … --start-fid … --end-fid … --out …`
  (由 `scripts/six_subsets_run.py` 逐段產生)。

## 4. 指標(全部由 `src/common/clip_metrics.py` 算,不另寫判定)

| 指標 | 適用 | 定義 |
|---|---|---|
| 目標召回率 | 全部 | 目標有標註框的取樣格中,被某條 track 以 IoU ≥ 0.5 配到的比例 |
| 連續率(主指標) | 全部 | 目標被配到且有編號的格中,編號等於片段內第一個編號的比例 |
| 排他率 | 多人 | 上述格中,同一幀沒有別的真人戴著同一個編號的比例。單人片段不可量測 |
| 編號切換次數 | 全部 | 逐鏡頭沿時間計算再相加 |
| 再取得率 | L2 | 離開前最後 k 格與回來後最前 k 格的多數編號相同的間隔對比例(k = 5、1) |
| 跨鏡頭一致率 | L3 | 兩台都有綁定的鏡頭對中,多數編號相同的比例 |
| 同時幀一致率 | L3 | 兩台以上同時綁到目標的幀中,編號完全相同的比例 |
| 誤偵框比例 | 全部 | 畫出來的系統框中沒配到任何真人的比例 |

- 彙總一律彙集逐格再算(分母才對),附 Wilson 95% 區間。
- 每個子集報三欄:全部、只含評估集序列、只含推導集序列。
- L3S 與 L3T 永遠分開報。

⚠ **連續率與多數率都無法否證「整段被綁成同一個錯誤編號」**;多人子集必須同時看排他率。

## 7. 這次不能回答什麼

- **與交接包的數字不能直接比大小**:它用標註軌跡(單鏡頭追蹤 100% 正確)、套了時間對應、候選人只含已出現過的人;
  這裡是真實偵測與追蹤、原始時間戳。指標名稱相同(連續率),前提不同。
- **逐片段獨立推論不等於實際部署**:每段從零開始、只給指名的鏡頭,沒有長時間累積的身份狀態。
  多人全長序列的誤併率(約 60%~85%)是另一個問題,本輪不重測。
- **現場泛化**:廚房為同款制服加口罩。
- 多人 L2 只有 17 段、L3T 只有 59 個目標,區間很寬。

### 8.5 怎麼讀

1. **單鏡頭(L1、L2)與平面圖幾何無關。** 差別全部來自 M4:外觀關聯(`single_person` 的 M4)把單人 L2 的再取得從 2/17 拉到 16/17、多人 L2 從 8/17 到 13/16。
2. **多人 L1 連續率只有 85%**,而且外觀關聯讓編號切換從 1,116 增加到 1,794 次。單鏡頭多人追蹤本身就不穩,這在跨鏡頭之前。
3. **多人 L3 的連續率會騙人。** `single_person` 連續率 71.9%、跨鏡頭一致 60.7%,看起來不差,但**排他率只有 35.9%** ——
   目標有編號的格子裡,將近三分之二同一幀有別的真人戴著同一個編號。那不是認對人,是把好幾個人併成一個。
4. **`plan_strict` 把排他率拉到 90%,代價是跨鏡頭幾乎接不上**(L3S 21.0%、L3T 0/59)。與全長序列的結論一致:位置證據嚴 = 不敢綁。
5. **`plan_share` 在多人上與 `single_person` 幾乎相同**(排他率 +4 點、一致率持平),在單人 L3 上明顯較好(連續率 69% → 95%、L3T 2/5 → 3/5)。
   多人 L3T 兩者完全相同:轉場時候選不在重疊鏡頭上,份額沒有作用的對象。
6. **沒有一組在多人 L3 同時拿到高一致率與高排他率。** 四組的(跨鏡頭一致, 排他率)是
   (31.7%, 56.3%)、(60.7%, 35.9%)、(21.0%, 90.1%)、(61.1%, 40.0%),落在同一條取捨線上。

### 8.6 與交接包數字的差距(前提不同,只能看量級)

| 多人子集 | 交接包(標註軌跡、+plan) | 本次最佳的連續率 | 本次同一組的排他率 |
|---|---|---|---|
| L3S | 0.904 | 72.8%(`plan_share`) | 40.0% |
| L3T | 0.981 | 72.2% | 48.3% |

交接包的 0.90 以上建立在「單鏡頭追蹤 100% 正確」上。換成真實追蹤後,多人 L1 的連續率就只有 85%、誤偵框佔兩到四成,
跨鏡頭的輸入本身已經不乾淨。**差距主要不在跨鏡頭的證據公式,而在進入 M5 之前的軌跡品質。**

### 8.7 這輪之後仍然不能回答什麼

§7 全部仍然成立。另外:排他率只在「目標被配到且有編號」的格子上量,沒有量到「被誤偵搶走編號」以外的錯綁型態;
多人 L1 / L2 的排他率 100% 只表示同一台鏡頭同一幀沒有兩個真人共用編號,不表示編號是對的。
