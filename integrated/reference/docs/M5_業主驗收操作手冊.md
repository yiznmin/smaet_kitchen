# M5 跨鏡頭身份 —— 佈署與驗收操作手冊

> 給實際佈署與測試的人。不需要讀懂演算法,照著做就能量出可信的數字。
> 每個步驟都有一個「做完怎麼確認」的檢查點。

---

## 這套系統在做什麼

廚師從 cam1 走出畫面、幾秒後出現在 cam2,系統要判斷**是不是同一個人**,
並給他一個全域的 `chef_id`。後面的食安事件(誰摸了生肉、有沒有去洗手)
全部掛在這個 id 上。

判斷錯有兩種,**後果完全不同**:

| 錯誤 | 後果 | 抓不抓得到 |
|---|---|---|
| **碎裂** 同一人被拆成多個 id | 事件序列斷掉、計時歸零 → 漏報 | ✅ 「身份數 ≠ 在場人數」就會告警 |
| **誤併** 綁到別人身上 | A 的行為記到 B 頭上 → **冤枉一個、放過一個** | ❌ **完全靜默**,下游 M7/M8 都驗不出來 |

所以驗收門檻對誤併嚴 5 倍。

---

## 佈署硬性規格(不滿足就不必往下做)

| 項目 | 規格 | 為什麼 |
|---|---|---|
| **人在畫面中的大小** | 高度 ≥ **畫面高度的 18%** | 低於此偵測率掉到 0.88 以下。⚠ 用畫面中**最遠最小**的那個人量,不是平均 |
| **推論解析度** | **1280**(不是預設的 704) | 704 只能到 26%,1280 可到 18% → 單台涵蓋面積**翻倍** |
| **鏡頭時鐘** | NTP 同步,鏡頭間殘餘偏移 **≤ 0.2 秒** | 2 秒偏移會讓誤拒率從 18% 跳到 49%,而症狀是「一直開新身份」,現場看不出原因 |
| **地面校正殘差** | **≤ 0.2 公尺** | ≥0.8 m 時這條證據完全無用。實測隨便標(±15px)也只有 0.08 m,不難達成 |
| **全景/廣角鏡頭** | 至少一台能俯瞰主要工作區 | 沒有它,4 人同時在場時會被**全部併成 1 個身份** |
| **視野重疊** | 盡量讓鏡頭之間**有重疊** | 重疊 = 直接看到同一個人;不重疊 = 只能猜他走了幾秒,誤差大得多 |

> ⚠ **系統是事後查詢用的,不需要即時**,所以 1280 推論的成本可以接受。

## 步驟一:填拓撲(哪台走得到哪台)

```bash
python scripts/build_camera_topology.py --template links.csv
```

打開 `links.csv`,每條「人可以走過去的路徑」填一列:

```csv
from,to,walk_distance_m,overlapping
cam1,cam2,8.0,no
cam2,cam1,8.0,no
cam1,cam3,,yes
```

**`walk_distance_m` 填的是「步行路徑距離」,不是直線距離。**
兩台鏡頭直線 3 公尺,但中間隔著中島要繞過去走 8 公尺 —— 要填 **8**。
這是最容易填錯、而且錯了會系統性低估的一項。

雙向請各填一列(來回距離可以不同)。視野重疊的鏡頭對 `overlapping` 填 `yes`,距離留空。

```bash
python scripts/build_camera_topology.py --csv links.csv --out configs/camera_topology.yaml
```

**檢查點**:腳本會印出換算後的轉場時間,並在下列情況警告 ——
轉場時間太短(與追蹤模組衝突)、只填了單向、距離不合理。**有警告先處理再往下。**

## 步驟二:地面校正(每台鏡頭)

在地面上挑 **≥4 個不共線**的可辨識點(磁磚角、設備腳、貼膠帶做記號)。
量它們在**廚房平面圖**上的座標(公尺,各鏡頭共用同一個原點),
再從各鏡頭的畫面截圖讀出它們的像素座標,填進 config:

```yaml
  cameras:
    cam1:
      clock_offset_s: 0.0
      homography:
        image_points: [[120, 700], [1150, 690], [980, 400], [300, 405]]
        world_points: [[0.0, 0.0],  [6.0, 0.0],  [6.0, 4.0], [0.0, 4.0]]
```

**不用填精度參數** —— 系統會自己從這些點算出標定殘差,並用它決定要多相信位置資訊。

> 地面校正同時解鎖**兩條**證據:人站在哪裡(位置),以及**人往哪個方向、多快在走**
> (軌跡)。後者是把誤併從 14.5% 壓到 5.6% 的關鍵 —— 兩個站在同一位置的人,
> 是從不同方向走過來的。config 裡 `velocity.window_s` 控制累積幾秒的軌跡:
> 1.0 秒拿到八成效益,2.0 秒最準但 chef_id 會晚 2 秒才給。

**檢查點**:跑步驟三的自檢,看 `A10_CALIB_QUALITY` 報的殘差:

| 殘差 | 判定 |
|---|---|
| ≤ 0.2 m | ✅ 可用 |
| 0.2~0.8 m | ⚠ 鑑別力下降 → 增加標定點、或先做鏡頭畸變校正 |
| ≥ 0.8 m | ❌ **完全無用** → 重標 |

> **沒做地面校正的後果**:實測 4 位廚師會被**全部併成 1 個身份**(誤併 72%,
> 8 人時 85%)。加了校正降到 14%。這是整套系統最關鍵的一步。

## 步驟三:自檢(還沒錄影就能做)

```bash
python scripts/audit_m5_config.py --headcount 4
```

它會在**還沒拍任何影片之前**抓出:拓撲填錯、單向連結、孤立鏡頭、
轉場時間與追蹤模組衝突、時鐘容忍度不足、地面校正品質不夠。

**檢查點**:**必須 0 個 ERROR 才能往下。** WARN 要逐條看過並確認可以接受。

---

## 步驟四:走動測試(產生真值)

```bash
python scripts/make_walktest_html.py --cameras cam1 cam2 cam3 --chefs 張師傅 李師傅 王師傅
```

用瀏覽器打開產生的 `walktest.html`(手機、平板都可以,離線可用)。

**測試設計:**
- **2~3 位人員**,穿**實際的工作制服**(不要故意穿不同顏色)
- 在鏡頭之間**來回走動** 20 分鐘以上
- 必須包含:**離開某鏡頭後隔一段時間再回來**、**兩人同時在場**、
  **兩人靠近彼此**(這是最容易出錯的情境)

**操作:**
1. 按「開始」的**同時**開始錄影 —— 兩邊時間必須對齊
2. 每人進入某鏡頭畫面時按該鏡頭,離開時再按一次
3. 不必精準到毫秒,±1 秒的誤差驗收腳本可以容忍
4. 匯出 CSV

**檢查點**:CSV 的區間數應該與實際走動次數相符;沒有「進入了卻沒離開」的紀錄。

---

## 步驟五:跑系統

```bash
python scripts/m5_track_video.py \
    --videos cam1.mp4 cam2.mp4 cam3.mp4 \
    --cameras cam1 cam2 cam3 \
    --weights /絕對路徑/checkpoint_best_regular.pth \
    --out results/m5_track/chef_events.jsonl
```

⚠ 權重必須用**絕對路徑**(相對路徑會被解析到模型快取目錄)。

**檢查點**:輸出的摘要會印「偵測到人 N 次」。**N=0 表示偵測整個沒作用**
(通常是類別編號對不上),先解決再往下 —— 這種錯誤不會自己報錯。

---

## 步驟六:驗收

```bash
python scripts/acceptance_m5.py --truth walktest.csv \
    --events results/m5_track/chef_events.jsonl --headcount 3
```

輸出三個數字,對照門檻:

| 指標 | 門檻 | 意義 |
|---|---|---|
| **IDF1** | ≥ 0.90 | 身份保持的整體品質(國際標準指標,第三方認得) |
| **碎裂率** | ≤ 5% | 同一人被拆成多個 id |
| **誤併率** | ≤ 1% | 綁到別人身上(靜默,所以門檻嚴 5 倍) |

門檻的來源:「未洗手」這類事件鏈約含 3 次跨鏡頭交接,要達到 80% 的召回
→ 每次交接的碎裂率須 ≤ 7.2%,留給偵測與追蹤的誤差預算後訂 5%。

**同時要看「身份數 vs 實際人數」** —— 系統報 1 個身份而現場有 4 個人,
表示**全部被併成一個**,那是最嚴重的失效,而碎裂率與誤併率**看不出來**。

## 出問題時怎麼查

| 症狀 | 先查什麼 |
|---|---|
| 一直開新身份(身份數 >> 人數) | ①時鐘沒同步 ②拓撲的轉場時間填太短/太窄 ③走的路徑沒填進拓撲 |
| 身份數 << 人數(全被併成一個) | **地面校正沒做或殘差太大** —— 這是最常見的原因 |
| 誤併偏高但校正沒問題 | 確認 config 的 `velocity.enabled: true`(它需要 ground_plane 才有作用) |
| 偵測到人 0 次 | 類別編號不對(微調權重=0、COCO 預訓=1) |
| 某條路徑的人一律被判新人 | 那條連結的轉場時間太短,與追蹤模組的緩衝衝突(自檢的 A3) |

每筆綁定決策在 `chef_events.jsonl` 裡都有 `score` 與 `n_candidates`,
可以事後查「為什麼綁成這樣」。

## 誠實說明:目前已知的限制

1. **誤併率約 5~8%,仍高於驗收門檻 1%。** 這是目前最大的已知缺口。
   歷程:一開始 72% → 加地面校正降到 14.5% → 加軌跡證據(速度)降到 **5.6%**。
   剩下的 5 倍缺口目前**沒有已知的演算法解**,需要靠流程手段補償
   (見下面的「若誤併率不可接受」)。
   · 原本「兩人相距 <0.5 m 時分不出誰是誰」的問題,已由軌跡證據解決 **81%**
     —— 兩人站在同一位置,但他們是從不同方向走過來的。
   · 代價:chef_id 的指派會**延後約 1 秒**(要先累積速度)。本系統是事後查詢用,
     可接受;若日後有即時告警需求則需重新評估。
   · 新的(較小的)誤差來源:兩個相隔 3 公尺以上、剛好朝同方向以相近速度移動的人,
     偶爾會被誤綁(約佔全部轉場的 1.7%)。
2. **外觀辨識幾乎沒有幫助。** 可商用的外觀模型在跨視角認人的準確率只有 11%
   (比隨機還差),而廚師穿同款制服更糟。所以系統靠的是空間與時間,不是「長得像」。
3. **目前的準確率數字全部來自模擬**,尚未用真實的多人資料校準。
   本手冊的步驟四~六就是為了取得那份資料 —— **你們的測試結果會用來修正這些預估**。
4. 全景鏡頭只負責「人」。刀具、砧板那類小物件在廣角下偵測會崩,
   **細節事件仍需近距鏡頭**,不能省。

## 若誤併率不可接受

模擬顯示演算法能做到約 **5%**,而食安追責的理想值是 1%。若貴方認定 5% 不可接受,
以下三條是可行的補償手段,依成本排序:

| 手段 | 作法 | 預期效果 | 成本 |
|---|---|---|---|
| **接受並在下游補償** | M6 事件標上信心度;彙總報表註明誤差範圍;針對性調查時人工看影片複核 | 不降低誤併率,但讓它**可見**而非靜默 | 最低 |
| **增加全景鏡頭** | 第二台不同角度的俯瞰鏡頭,消除單一視角的遮擋 | 未測,推估可再降 1/3 | 中(一台鏡頭) |
| **可辨識標記** | 帽子/圍裙上不同顏色色塊,或 AprilTag 之類的視覺標記 | **可望接近 0%** —— 把「認人」變成「認標記」 | 需人員配合,但無授權與隱私問題 |

⚠ **不建議人臉辨識**:可商用的模型授權不乾淨,且涉及生物特徵個資,
本專案自始未採用。
