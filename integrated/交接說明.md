# 智慧廚房 M1~M5 整合版 交接說明

- 整理日期:2026-10-13
- 適用對象:接手本專案 M1~M5 的人(需會 Python 與基本命令列)
- **這個資料夾可以單獨使用**,不需要完整 repo。所有路徑皆相對於本資料夾
- 路徑後面標「(repo)」的,表示該檔不在本資料夾內,只存在完整 repo(GitHub `yiznmin/smaet_kitchen`)

---

## 1. 先看這四件事

1. **執行所需的東西都在這個資料夾裡**:進入點程式、設定檔、各模組原始碼、M3 微調權重、預訓練權重、示範用的偵測快取。唯一要自備的是影片與 Python 環境。
2. **預設設定(`delivery`)是多人場景目前成本最低的一組,但離驗收門檻很遠**:多人 7 序列誤併率約 59%,門檻是 1%。M5 在多人場景尚未解決。
3. **`single_person` 設定只在畫面裡只有一個人時成立**。同一組設定在多人全長序列上誤併率 59.5% 升到 83.0%,不可用於多人。
4. **M2 與 M3 在這之前從未串在同一支程式裡**。整合版補上了串接,但 M2 閘門(無動態就不跑 M3)沒有經過任何 M4/M5 評估,預設關閉。

## 3. 怎麼跑

### 3.1 環境

- Python 3.11(不要用 3.13 以上)。
- `torch` 要依機器的 CUDA 版本手動安裝,再 `pip install -r requirements.txt`。細節與版本見 `requirements.txt`。
- 驗證時的版本:rfdetr 1.9.4、torch 2.11.0+cu128、supervision 0.29.1、trackers 2.6.0、numpy 2.4.6。
- Windows 終端機是 cp950,執行前先設 `PYTHONIOENCODING=utf-8`,否則中文輸出會出錯。
- 預訓練權重已自帶,第一次執行不需要連網下載:
  - DINOv2 直接從 `weights/pretrained/torch_hub/` 載入。
  - RF-DETR 的 COCO 預訓權重,程式會在第一次需要時複製一份到使用者家目錄的 `.roboflow/models/`(rfdetr 固定從那裡讀)。只帶了 nano。
- M2 分支 B 的分類器需要 `onnxruntime`,但目前沒有權重,不裝也能跑。

### 3.2 先確認環境裝對了

用自帶的偵測快取重跑示範片段(需要 CHIRLA seq_025 的 camera_1 到 3 三支影片,不需要 GPU):

```
python run_pipeline.py \
    --videos <camera_1.avi> <camera_2.avi> <camera_3.avi> \
    --cameras camera_1 camera_2 camera_3 \
    --det-cache demo/det_cache/seq_025 \
    --start-fid 1780 --end-fid 1890 \
    --out outputs/demo
```

`outputs/demo/` 的 `tracks.csv`、`track_events.csv`、`chef_events.jsonl` 應該與 `demo/expected/delivery/` 的同名檔案內容完全相同。加上 `--profile single_person` 再跑一次,應與 `demo/expected/single_person/` 相同。

### 3.3 跑自己的影片

廚房影片,微調 11 類權重,即時偵測:

```
python run_pipeline.py \
    --videos <a.mp4> <b.mp4> --cameras cam1 cam2 \
    --weights weights/m3_nano_r2_armA/checkpoint_best_total.pth \
    --topology <該場地的拓撲檔> \
    --out outputs/kitchen
```

- 不給 `--weights` 就用 COCO 預訓權重,只偵測人。M4/M5 在 CHIRLA 上的數字都是這個模式。
- 不給 `--topology` 就用設定檔內嵌的 CHIRLA 七鏡頭拓撲。**換場地一定要換拓撲**,否則 camera_id 對不上,跨鏡頭一律開新身份。拓撲檔格式可參考 `reference/configs/fix_grid/base.yaml`。
- 其他常用參數:`--profile`、`--stride`、`--max-loops`、`--thr`、`--resolution`、`--embedder`、`--gate-m3`、`--save-frames`、`--save-frames-every`。沒給的一律用設定檔的值。
- 除了影片路徑,設定檔與命令列裡的相對路徑都相對於本資料夾。

#### 微調權重的來歷與準確度(2026-10-13)

本機重訓的 Arm A(建議使用):

- 設定:nano、COCO 預訓起始、60 epochs、解析度 704、batch 4、grad_accum 4、lr 1e-4,與 `notebooks/m3_experiment_staged_vs_epfl.ipynb`(repo) 的 Arm A 相同。
- 資料:`m3_finetune_r2`(train 360 / valid 90 / test 90,EPFL round2)。
- 腳本:`scripts/train_m3_rfdetr.py`;環境:另建的訓練用虛擬環境(rfdetr 1.9.4 加訓練相依,與推論環境分開,原因見 `requirements.txt`)。
- 耗時 25.3 分(RTX A6000)。valid mAP@50:95 為 0.7467,EMA 0.7577(文件記載的 Arm A 是 0.7356 / 0.7636)。
- 權重在 `weights/m3_nano_r2_armA/`,同目錄帶了 `metrics.csv`、`train_args.json`、`training_config.json`(完整的訓練紀錄與其他檢查點留在原機器,沒有帶進來)。採用 `checkpoint_best_total.pth`(rfdetr 依 valid 選出的最佳,這次是 EMA 版)。

test 90 張(828 框),IoU 0.5。原始結果在 `reference/results/m3_acc/resolution_compare_armA_20261013.json` 與 `resolution_compare_20261013.json`。

| 權重 | 推論解析度 | 統一門檻 0.3 的 P / R / F1 | 食安類 recall |
|---|---|---|---|
| 舊 `model_result/nano`(repo) | 384 | 0.553 / 0.467 / 0.506 | 0.488 |
| 舊 `model_result/nano`(repo) | 704 | 0.632 / 0.553 / 0.590 | 0.598 |
| 新 Arm A(regular) | 384 | 0.826 / 0.818 / 0.822 | 0.813 |
| 新 Arm A(regular) | 704 | 0.911 / 0.931 / 0.921 | 0.911 |
| 新 Arm A(total,採用) | 384 | 0.808 / 0.842 / 0.824 | 0.825 |
| **新 Arm A(total,採用)** | **704** | **0.903 / 0.942 / 0.922** | **0.923** |

採用權重在 704 下的逐類 P / R(統一門檻 0.3):人 1.00 / 0.99、刀具 0.88 / 0.92、砧板 0.86 / 0.80、食材 0.85 / 0.94、鍋鏟 0.91 / 0.95、鍋子 0.94 / 0.95、手 0.83 / 0.89、容器 0.91 / 0.96、抹布 0.98 / 1.00。

這次量測確認的三件事:

1. **文件上的 F1 0.81 是在 384 下量的。** 新 Arm A 在 384 下是 0.822,與文件記載的 0.807 相符;同一顆權重改用 704 推論是 0.922。
2. **推論解析度必須與訓練一致。** rfdetr 在不傳 `resolution` 時會把位置編碼內插到變體預設值(nano 384),不報錯。整合版改為 `resolution: auto`,自動採用權重的訓練解析度。
3. **repo 原有的 `model_result/nano`(repo)、`model_result/medium`(repo) 是早期小資料權重。** 它們的輸出目錄是 `/content/out_nano`、`/content/out_medium`,只訓練了 185 與 152 步,對應 2026-07-23 的一鍵比較,不是 round2。同條件下 F1 只有 0.590,不建議再用。

逐類門檻:

- 設定檔的值是依 `scripts/sweep_thresholds.py` 的規則在 valid 上掃的(食安類在 precision 不低於 0.6 下取最大 recall,其餘取最大 F1)。套到 test 是 P 0.884 / R 0.929 / F1 0.906,食安類 recall 0.932。
- 這個規則偏向 recall,所以整體 F1 比統一門檻 0.3(0.922)略低。「手」的門檻被壓到 0.1,test precision 降到 0.62。要整體 F1 最高就全部用 0.3。
- `reference/configs/m3_thresholds.json` 是舊值(掃的權重與解析度都沒有紀錄),沒有更動。

對照 `reference/docs/M3_訓練SOP_迭代式_20260806.md` 的驗收目標(食安類 recall 至少 0.90):採用權重在 704、設定檔門檻下,人 0.99、刀具 0.92、食材 0.94、手 0.91 達標,砧板 0.82 未達標。

限制:

- test 只有 90 張,且與訓練資料來自同一批 EPFL 影片(同場次、同視角),數字不代表真實廚房的表現。
- 只訓練了一次。文件記錄過同設定重跑會有起伏。
- 模型載入已集中到 `src/m3/model.py` 的 `load_rfdetr()`,預設依權重的訓練解析度推論。`scripts/m3_on_frame.py`、`sweep_thresholds.py`、`m4_track_video.py`、`m5_track_video.py`、`cache_detections.py`、`reid_eval_epfl.py` 與整合版都改用它,並加了 `--resolution`(`auto` / `default` / 整數)。沒給微調權重時行為不變。
- 因此 2026-10-13 之前用微調權重跑出來的結果(都是 384)要重現時,必須加 `--resolution default`。
- M4/M5 在 CHIRLA 上的數字用的是 COCO 預訓 nano(原生 384),不受影響。

## 10. 這個專案的工作規矩

1. **預先登記**:實驗前把設定、判準、可被否證的預測寫成文件並提交 git,跑完只追加結果段。
2. **推導集與評估集分開**:可調參數只能用推導集估。
3. **真值不得進決策**。唯一例外是 `--oracle-cue`,它的數字不可與正式評估並列。
4. **修法最多 3 輪**,無效就停,交由負責人決定。
5. **新功能預設關閉**,關閉時輸出必須與基準逐位相同。
6. **量不到就寫「不可量測」**,不可印 0% 或 100%。L3S 與 L3T 永遠分開報。
7. 每份報告都要有「這次不能回答什麼」的段落。
