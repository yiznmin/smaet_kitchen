# 六個子集測試結果

- 測試日期:2026-10-13
- 適用對象:接手 M1~M5 的人。先讀過 `交接說明.md` 第 1 節再看這份
- 路徑皆相對於本資料夾;標「(repo)」的檔案只在完整 repo 裡

---

## 1. 結論

1. **單鏡頭(L1、L2)可用,跨鏡頭多人(多人 L3)不可用。** 四組設定在多人 L3 沒有任何一組同時做到「跨鏡頭給同一個編號」和「不把別人併進同一個編號」。
2. **建議的預設不變**:多人場景用 `delivery`,只有一個人的場景用 `single_person`。兩組平面圖設定(`plan_strict`、`plan_share`)都不採用。
3. **`plan_share` 在單人跨鏡頭上比 `single_person` 好**(L3S 連續率 69.1% → 95.4%),多人上沒有好處。樣本只有 17 段,還不足以改預設。
4. **全長連續跑(最接近實際部署)四組都離驗收門檻很遠。** 誤併率 37%~87%(門檻 1%),正確率最高 15.59%。數字見 4.6 節。
5. **換成 M3 微調權重後,在 CHIRLA 上漏偵大增**(多人單鏡頭召回 93% → 60%),誤偵減半,全長誤併率幾乎不變。這顆權重是為廚房訓練的,不適合當 CHIRLA 上的偵測來源。數字見 4.7 節。
6. **瓶頸在進入 M5 之前。** 多人單鏡頭的連續率只有 85%,畫面上的框有兩到四成不是人。跨鏡頭的輸入本身就不乾淨。

## 2. 測了什麼

| 項目 | 內容 |
|---|---|
| 資料 | CHIRLA,7 台鏡頭,10 個序列 |
| 六個子集 | 單人 / 多人 × L1(單鏡頭連續)/ L2(單鏡頭離開再回來)/ L3(跨鏡頭) |
| 片段數 | 1,657 筆「片段 × 目標」,來自 1,018 個時間窗 |
| 執行方式 | 每個時間窗各跑一次 `run_pipeline.py`,只給該段的鏡頭與幀範圍,狀態從零開始 |
| 執行次數 | 1,018 個窗 × 4 組設定 = 4,072 次,失敗 0 次 |
| 偵測 | COCO 預訓 RF-DETR nano 的偵測快取,門檻 0.10,每 5 幀取 1 幀 |

L3 再分兩種,永遠分開看:

- **L3S**:同一個人同時被兩台鏡頭看到。
- **L3T**:同一個人先離開一台,之後才出現在另一台。

四組設定(`pipeline_config.yaml` 的 profile):

| 設定 | M4 追蹤 | M5 外觀 | M5 拓撲 |
|---|---|---|---|
| `delivery` | C-BIoU | 不用 | 原拓撲 |
| `single_person` | 外觀關聯(DINOv2,權重 0.7) | DINOv2 | 修正拓撲 |
| `plan_strict` | 同 `single_person` | DINOv2 | 修正拓撲 + 平面圖位置證據(位置對不上就不綁) |
| `plan_share` | 同 `single_person` | DINOv2 | 修正拓撲 + 平面圖位置證據(候選有多人時,依位置決定分給誰) |

## 3. 指標怎麼看

| 指標 | 意思 |
|---|---|
| 召回 | 目標有標註框的畫面格中,系統有框到他的比例 |
| 連續率 | 目標有編號的畫面格中,編號等於他在這段裡第一個編號的比例 |
| 排他率 | 目標有編號的畫面格中,同一幀沒有別的真人戴著同一個編號的比例。只有多人片段量得到 |
| 再取得 | L2 專用:離開再回來,前後是同一個編號的次數 |
| 跨鏡頭一致 | L3 專用:兩台鏡頭給目標的多數編號相同的鏡頭對比例 |
| 同時幀一致 | L3S 專用:兩台同時看到目標的幀中,兩邊編號相同的比例 |
| 多數率 | 目標有編號的畫面格中,編號等於他在這段裡最常出現的那個編號的比例。只當輔助:中途換號後穩定在錯的編號也會算對 |
| 綁定率 | 目標有標註框的畫面格中,被框到而且那個框有編號的比例 |
| 編號切換次數 | 目標的編號沿時間改變的次數,逐鏡頭計算再相加 |
| 不同編號個數 | 目標在各段拿過的編號數加總。理想值等於片段筆數(每段一個) |
| IoU | 系統框與標註框的重疊程度,1 為完全重合。配對門檻是 0.5 |
| track 切換次數 | 單鏡頭追蹤把目標換成另一條軌跡的次數(M4 的斷軌) |
| 誤偵框比例 | 畫出來的系統框中,沒有配到任何標註真人的比例 |
| 目標拿到編號前已開的編號數 | 目標第一次被綁定之前,系統已經發出幾個編號。大於 0 表示有別的框先搶到編號 |

**多人片段一定要把連續率、跨鏡頭一致和排他率一起看。** 系統如果把畫面上所有人都併成同一個編號,連續率與跨鏡頭一致會是 100%,只有排他率會掉下來。

#### 怎麼讀

- **微調權重在 CHIRLA 上漏掉很多人。** 目標召回率在單人 L1 從 95.9% 掉到 83.5%,多人 L1 從 93.2% 掉到 60.4%,多人 L2 從 78.1% 掉到 45.3%。

  所以這些率上升不等於系統認人變準。把召回一起看:多人 L3S 的 `single_person` 連續率 71.9% → 79.2%,但召回 93.1% → 79.4%。
- **全長的誤併率幾乎沒變**(`single_person` 83.40% → 82.75%、`plan_strict` 37.11% → 37.48%)。
  沒有對到真人的 track 少了六到七成,誤併率卻沒有跟著降,表示多人誤併的主因不是誤偵,而是 M5 把真人彼此綁錯。

- **結論:這顆微調權重不適合直接拿來當 CHIRLA 上 M4/M5 的偵測來源。** 它漏掉的人太多。它是為廚房訓練的,在廚房的表現這次沒有量到。

## 7. 平面圖幾何為什麼沒有解決多人問題

平面圖幾何是把各鏡頭的人投影到同一張場地平面圖上,用「兩台看到的人是不是站在同一個位置」當證據。

- 同一個人在兩台鏡頭投影到平面圖後,位置差的中位數是 11~25 像素,而一個房間才寬約 86 像素。這個精度不足以分辨站得近的兩個人。
- 位置證據要求得嚴,真的同一人也會被擋掉(`plan_strict`);要求得鬆,旁邊的人也會被接受(`plan_share`)。
- L1、L2 是單鏡頭片段,平面圖證據完全不介入,兩組平面圖設定與 `single_person` 的數字完全相同。

詳細的兩輪實驗在 `reference/docs/M5_平面圖幾何接入_預先登記_20261013.md`。

## 8. 讀這些數字時要知道的限制

- **逐片段獨立推論不等於實際部署。** 每段從零開始、只給指名的鏡頭。實際部署是 7 台長時間連續跑,身份狀態會累積;那個情境下多人誤併率是 60%~85%(`交接說明.md` 5.1 節)。
- **與外部交接包的數字不能直接比。** 外部交接包在同一批多人 L3S 片段上量到連續率 0.904,這裡最好是 72.8%。它用人工標註的軌跡當單鏡頭追蹤結果(等於追蹤 100% 正確),這裡是真實偵測與追蹤。
- **CHIRLA 每個人衣著不同**,廚房是同款制服加口罩。以上數字是上界。
- **樣本小的子集**:單人 L3T 5 段、單人 L3S 12 段、多人 L2 17 段、多人 L3T 59 筆。
- **預測紀律有一處瑕疵**:提交預先登記之前,為了確認腳本能跑,先看過 6 個時間窗(seq_000 的多人 L3S)的數字。
- 排他率只量「同一幀有沒有別的真人共用編號」,量不到跨時間的錯綁。

```
python run_pipeline.py --profile plan_share --seq seq_025 \
```

```
python scripts/six_subsets_manifest.py      (repo)
python scripts/six_subsets_run.py --workers 12      (repo)
python scripts/six_subsets_eval.py      (repo)
```

- 需要 CHIRLA 的影片、標註與 10 個序列的偵測快取。
- 4,072 次執行在平行 12 的情況下約 2.6 小時。
