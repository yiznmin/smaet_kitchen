# M3 模型選型 — 綜合現況總表與下一步

> 彙整所有已評估模型的**速度 + 準確度**,並列出下一步。數據來源:Phase 1(速度)+ Phase 2(準確度)。
> 環境:RTX 3050 4GB / onnxruntime-gpu(速度)+ 原生框架 CPU(準確度);資料:Roboflow 廚房(未微調)。

---

## 0. 重大定位更新(2026-06-07):系統=事後查詢 → **準確度優先**

使用者確認:本系統為**事後查詢/追溯,非即時警報**。因此選型最佳化目標從「速度」改為「**準確度優先**」:
- 速度**不再是硬限制**(每幀可慢);**可用高解析度 + 準確度導向模型(RF-DETR)**。
- 但「把整批錄影跑完」的**總成本**仍重要 → **M2 動態過濾(省 58.9%+)更關鍵**。
- → 下方「綜合定位」中**速度權重下降**;**準確度單項冠軍 RF-DETR(medium/nano)上升為首選方向**。

**小物件模擬實驗(2026-06-07)**:把物件人工縮小,刀 AP 從 0.21 崩到 **0.02**(縮 1/4 時)。
→ 證實**俯視遠距下現成模型對刀必失效**。詳見 `docs/M3_小物件模擬結果.md`。

**解析度回升實驗(2026-06-07)**:對縮小後的圖提高輸入解析度,rfdetr_nano 刀 AP **0.024 → 0.153(約 6×)**回升。
→ **高解析度能救小物件(方向正確)**,但 (a) 有「救小傷大」取捨;(b) **RF-DETR 比 D-FINE 更耐高解析度**(dfine 在 1280 崩);
(c) 回升後仍只 ~0.15 → **高解析度有用但不夠,仍須微調**。詳見 `docs/M3_解析度回升結果.md`。

→ **綜合策略(事後查詢):RF-DETR + 較高解析度 + 在目標解析度微調**。

## 2. 兩維度的核心結論

- **速度**:D-FINE 系列在同條件(公平 672)最快、最省記憶體。
- **準確度**:RF-DETR 系列最準(mAP50 0.62–0.63)。
- **綜合(各原生解析度)**:**rfdetr_nano** 最平衡 —— 既快又準,刀 AP 也最高。
- **共同的硬傷**:**小餐具(刀/叉/匙)AP 僅 0.1–0.2**,而大家電 ~0.7。現成模型對「廚師手上的小工具」都不夠準。

---

## 3. 現況限制(數據效力)
1. **速度數字在 RTX 3050**(非部署主機)→ 相對排名可信、絕對值待目標主機複核。
2. **準確度在「未微調的現成 COCO 模型 + 家用廚房照片」** → 非商用俯視鏡頭、非優化後;刀樣本少、排名波動大。
3. **缺 person / cutting_board / 生肉** → 主目標(廚師)與交叉污染核心物件尚未評估。

## 4. 下一步(優先序)

| 優先 | 行動 | 為什麼 | 產出 |
|---|---|---|---|
| 🥇 1 | **取得/自標完整廚房資料**:含 person、knife、cutting_board、raw_meat,且為**實際部署鏡頭視角(俯視商用廚房)** | 現有資料缺主目標與核心物件;小物件(刀)現成模型不夠準,必須有對的資料才能微調與驗證 | 標註資料集 |
| 🥈 2 | **微調(fine-tune)準確度導向模型**(RF-DETR 為主,因事後查詢=準確度優先)在廚房資料上,重評 knife/cutting_board/raw_meat AP | 把刀的 AP 從 ~0.2 拉到可部署;這是讓系統「抓得到廚師手上的刀」的關鍵 | 微調權重 + 準確度報告 |
| 🥈 2b | **解析度回升實驗**:對縮小後的圖把輸入解析度拉高,看 knife AP 是否回升 | 事後查詢可用高解析度;先驗證高解析度救小物件是否有效,再決定部署解析度 | smallobject 解析度對照 |
| 🥉 3 | **確認目標部署主機 GPU**,在該機複核(事後查詢看的是「跑完整批錄影的總時間/成本」,非每幀即時) | 估算處理一天錄影要多久、配合 M2 過濾降本 | 處理吞吐估算 |
| 4 | **定案 M3 選型**(速度×準確度×微調結果合併) | 三者齊全才拍板 | 選型決議 |
| 5 | **推進 M4 追蹤(ByteTrack)→ M5 Re-ID → M6 事件規則** | 把 pipeline 帶進時間維度,實作食安事件(停留、交叉污染) | 後續模組 |

> **最關鍵的一步是 1+2(資料 + 微調)** —— 速度與「現成準確度」都摸清楚了,真正卡住食安用例(可靠偵測刀)的是「用對的資料微調」。
