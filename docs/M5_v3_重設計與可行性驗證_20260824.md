## 1. 起點:三個比預期更根本的缺口

盤點既有程式碼時發現的,不是推測:

1. **M4 與 M5 從未接線**。全 repo 沒有任何檔案同時 import `m4_track` 與 `m5_reid`,
   沒有「影片 → 追蹤 → chef_id」的端到端腳本。M5 從來沒在真實影片上跑過。
2. **`configs/camera_topology.yaml` 與 `reid.yaml` 沒有任何程式讀取**。
   `verify_m5_st.py` / `demo_m5_st.py` 各自硬寫一份 dict,值恰好相同 —— 於是改
   config 不影響行為、改腳本不反映到部署,兩邊可以無聲地各說各話。
   原本規劃「交給業主填 config」,填了不會生效。
3. **EPFL 6 身份實測有 session confound**。一個場次一人 → 「身份」等於「錄影場次」,
   同一人所有 crop 同衣服同光照。OSNet 的 92.65% 應視為**偏樂觀的上界**。

## 2. 方法:解析 → 實證對拍 → 模擬

刻意排成這個順序。理由:模擬器的可信度上限等於它的假設,而解析式與實證對拍的
可信度不依賴假設。先用解析式排除「連理想情況都不合格」的參數空間,再用模擬
回答「在什麼條件下會壞」。反過來做的話,模擬會先給出一堆漂亮曲線,然後被解析式
的算術全部作廢。

### 2.1 解析式閘門容量分析(`scripts/analyze_gate_capacity.py`)

不需任何資料、不需 GPU,秒級得到可行/不可行訊號。七節:

| 節 | 回答 |
|---|---|
| §1 | 有效門寬與誤拒率 |
| §2 | 候選多重度 E[C] —— 決定外觀重不重要 |
| §3 | M4 `lost_track_buffer` 與轉場時間的隱藏耦合 |
| §4 | 時鐘漂移容忍度 |
| §5 | **與真實程式碼對拍**(解析式的正確性檢查) |
| §6 | 光靠重配權重救不救得回來 |
| §7 | v2 vs v3 實測門寬 + 三個約束 |

**§5 是這份分析可信的關鍵**:用真實的 `SpatioTemporalIdentityManager` 反推實測
門界,與解析值比對,誤差 0.002~0.004(= 掃描步長 0.005)。解析式若與實作不符,
以實作為準、前四節作廢 —— 這條規則寫進腳本裡。

### 2.2 蒙地卡羅(`scripts/sim_m5_montecarlo.py` + `src/m5_sim/world.py`)

三個反循環論證的措施:

1. **世界模型與系統模型是不同的分布族,且不共用參數。**
   世界用**對數常態 + 逗留 + 繞路**;系統用它自己以為的高斯/逗留混合。
   `src/m5_sim/world.py` **刻意不 import `m5_reid.evidence`**。
   掃描的維度是**失配程度**,不是絕對值。
2. **五組消融同吃一個世界**:全開新 / 純外觀 / 純時空 / 完整 / oracle。
   完整系統必須落在(純外觀、純時空)與 oracle 之間,否則模擬器本身有問題。
   這條檢查寫進腳本,不通過就 `exit 1`。
3. **兩個世界參數從真實資料校準**(報告中標明「這兩個不是我們編的」):
   外觀分布用 EPFL 449 crops 實測值;M4 缺陷率預留 `m4_defect_rates()` 讀實跑軌跡。

## 3. 發現一:v2 的加權和有結構性缺陷

### 3.1 `k_sigma` 是死參數

```
fused = 0.7·exp(-0.5z²) + 0.3·app ≥ 0.35        z = (Δt-μ)/σ
另有硬門 |z| ≤ k_sigma = 2.0
```

解出來:`k_sigma` 只有在外觀 cosine ≥ **0.851** 時才是實際生效的門。
DINOv2 實測跨視角同人平均 **0.490**、OSNet **0.618** —— 兩者都達不到。
所以 `k_sigma` 在真實運作中幾乎從不觸發,**真正淘汰候選的一直是 `combined_threshold`**。
兩道門互相遮蔽,其中一道是裝飾品。

### 3.2 理想假設下就已經不達標

| 外觀 cos | 有效門寬 \|z\| | 高斯覆蓋率 | 誤拒率 |
|---|---|---|---|
| 0.00 | 1.1774 | 76.1% | **23.9%** |
| 0.20 | 1.3276 | 81.6% | **18.4%** |
| 0.49(DINOv2) | 1.5735 | 88.4% | **11.6%** |
| 0.90 | 2.0000 | 95.4% | 4.6% |

μ/σ 完全正確、轉場真為高斯、時鐘完全同步、無逗留無繞路的**最有利**條件下,
DINOv2 量級的碎裂率仍有 **11.6%**,而由 M6 反推的預算是 5% —— 差 2.3 倍。

### 3.3 三個約束共用一個旋鈕

| | 要求 | 靠什麼調 |
|---|---|---|
| C1 碎裂率 ≤ 5% | 時間窗要夠寬 | 壓低 `thr` |
| C2 外觀不能單獨過門 | `w_app < thr` | 壓低 `w_app` |
| C3 外觀要能破平手 | `w_app` 擺幅夠大 | 提高 `w_app` |

同一個 `thr` 同時控制「窗多寬」與「外觀能不能單獨過門」→ 放寬窗要壓低 `thr`,
壓低 `thr` 又得同步壓低 `w_app` 才能維持硬門性質,而壓低 `w_app` 就削弱破平手。
掃參數空間確認有解(`w_st=0.7, w_app=0.1, thr=0.12`,碎裂 3.2%),但**是取捨不是免費的**
—— 外觀擺幅從 ±0.30 壓到 ±0.10。

> 過程紀錄:第一次掃描把 `w_app` 固定在 0.3,結論是「無解」;放開後才發現有解。
> 「無解」是掃描設限造成的假象,已修正。

## 4. v3:likelihood ratio 融合

### 4.1 設計

兩個互斥假設的證據累加:

```
H1:這條新 track 就是那位剛離場的廚師
H0:這是一位與該廚師無關的人(背景到達)

LLR = log p(Δt|H1) − log λ_bg  +  log p(cos|同人) − log p(cos|不同人)
      └───── 時間證據 ─────┘     └────── 外觀證據 ──────┘
```

實作:[`src/m5_reid/evidence.py`](../src/m5_reid/evidence.py)

魔數 `0.35` 換成兩個**物理上可量測**的參數:

| 參數 | 意義 | 怎麼量 |
|---|---|---|
| `background_arrival_hz` | 「真正的新人」在單一鏡頭出現的速率 | 數一小時有幾個不屬於任何已追蹤廚師的人入鏡 |
| `cost_false_merge_over_break` | 誤併比碎裂嚴重幾倍 | 由 M6 的事件後果推導 |

轉場分布抽換式:`GaussianTransit` / `LoiterMixtureTransit`(預設)/
`HistogramParzenTransit`(從實測樣本估,st-ReID 作法,未來校準用)。

### 4.2 效果(實測,非推算)

| 外觀 cos | v2 \|z\|max | v2 碎裂率 | v3 \|z\|max | v3 碎裂率 |
|---|---|---|---|---|
| 0.00 | 1.170 | 24.2% | 2.170 | 3.0% |
| 0.20 | 1.320 | 18.7% | 2.470 | 1.4% |
| **0.49** | 1.570 | **11.6%** | 3.050 | **0.2%** |
| 0.90 | 2.000 | 4.6% | 4.990 | 0.0% |

三個約束同時成立:

- **C1** 碎裂率 0.2% ≤ 5% ✅
- **C2a** 物理不可能(同鏡頭 / 無連結 / 早於離場)+ 外觀 cos=1.0 → 必拒 ✅
- **C2b** 荒謬延遲(20×μ)+ 外觀 cos=1.0 → 必拒 ✅
- **C2c** 外觀最大證據 1.31 nats < 判定門檻 1.61 nats → 單獨過不了門 ✅
- **C3** 時間相同時外觀破平手 ✅

### 4.3 一個自動性質

C2c **不是調參調出來的**。DINOv2 本身就只有 1.31 nats 的鑑別力,所以它過不了門。
**模型有多少資訊量,就自動獲得多少發言權** —— v2 用固定 `w_app=0.3` 硬塞時做不到。

⚠ 反過來:OSNet(約 4.99 nats)或 TAO 會**超過**門檻,可以單獨推翻中等強度的
時間證據。屆時要用 `appearance_clip` 夾住,或重新推導成本比。選型時要一併決定。

### 4.4 v3 引入又修掉的回歸

自檢工具第一次跑就報 ERROR:**有效窗下界 0.02 秒** —— 「離開後 0.02 秒抵達 4 秒
路程的鏡頭」會被接受。原因是 v3 拿掉 `k_sigma` 硬門後只剩 `dt > 0`,而
`LoiterMixtureTransit` 沒實作 `max_z` 截斷。

修法:在 `TransitModel` 基底加**硬物理下限** `hard_min = 0.3 × μ`
(μ 以廚房步速 0.9 m/s 推得,全力奔跑約 3 m/s → 最快約 μ 的 0.3 倍)。
這道約束在 `logpdf` 之前就擋掉,**證據權衡碰不到它** —— 「人不能瞬移」屬於物理,
不屬於可以用相似度買通的事。修完下界變 1.20s。

## 5. 發現二:四個實際的 bug

| # | 問題 | 後果 | 狀態 |
|---|---|---|---|
| B1 | M4 的 `lost_track` 在短暫遮擋就觸發,而 track 從 lost 恢復時**不發任何事件**(`new_track` 只認 `active_ids - _seen_ids`,`_seen_ids` 是累積的) | M5 把 chef 標成 gone 後**永遠卡住**,綁定永久遺失。廚房遮擋極頻繁 → 最高頻且完全靜默的失效路徑 | ✅ 新增 `reacquired` 事件 + 三段式離場語意 |
| B2 | `_exit` 字典從建立後從未被移除(`tick()` 只清 `self.gone`) | 常駐記憶體隨累計人次單調成長。實測 300 人次全部逾 TTL 後 `gone=0` 但 `_exit=500` 筆殘留 → **直接違反 spec L103 第三條驗收標準** | ✅ 加 `_forget()` hook |
| B3 | 出口時間戳若取自 `removed` 而非 `lost` | 離場時間系統性延後約 `lost_track_buffer/fps`,所有轉場 Δt 偏小 → 時間窗判斷失準 | ✅ 取 pending exit 的時間戳 |
| B4 | 鏡頭時鐘漂移完全未處理 | 2 秒漂移在 σ=1.5s 下 = 1.33σ,誤拒率從 18% 跳到 **49%**。症狀是「chef_id 一直開新的」,看起來像模型爛 | ✅ `clock_offset_s` + 自檢 + skew 反推 |

### 離場語意三段式(B1/B3 的修法)

| M4 事件 | 觸發時機 | M5 的反應 |
|---|---|---|
| `lost_track` | 進 ByteTrack lost | 記**預備出口**,不標 gone |
| `reacquired`(新增) | 從 lost 回到 active | 撤銷預備出口,chef 維持 active |
| `removed` | lost buffer 到期 | 真正標 gone,**出口時間戳用 lost 當時的** |

## 6. 發現三:蒙地卡羅 —— 碎裂不是參數問題,是結構缺口

執行條件:4 位廚師 / 1.5 小時 / 20 次重複 / 共 **6468 次轉場**。
原始輸出 `results/m5_reid/sim_full_run.txt`。

### 6.1 消融對照

| 系統 | IDF1 | 碎裂率 | 誤併率 | ID 切換 |
|---|---|---|---|---|
| (a) 全開新(基線) | 0.012 | 100% | 0% | 323.4 |
| (b) 純外觀 | 0.012 | 99.9% | 0.1% | 323.4 |
| (c) 純時空 | 0.150 | 23.3% | 5.5% | 93.4 |
| (d) 完整系統 | 0.148 | 24.1% | 5.4% | 95.5 |
| (e) oracle(知道真分布) | 0.162 | 20.8% | 6.5% | 88.3 |

- 健全性檢查通過(完整系統落在消融組與 oracle 之間)
- **M5 模組的價值 = +0.136 IDF1**(相對於完全不做身份綁定)
- **參數失準的代價只有 +0.014 IDF1** —— 就算系統完全知道真實轉場分布也只好這麼一點。
  這表示**瓶頸不在參數估計,在架構**。
- **純外觀 ≈ 全開新**,完全沒有貢獻

> ⚠ **IDF1 與觀測時長有關,不可跨時長比較。** 每次轉場的碎裂率固定時,
> 時間越長累積的碎裂越多、IDF1 越低(同一組設定下 0.5 小時得 0.33、1.5 小時得 0.15)。
> **與時長無關的量是 `p_break` / `p_false_merge`**,對外報告應以那兩個為主,
> IDF1 只在標明時長後才有意義。

### 6.2 失效分解(本輪最有價值的產出)

| 成因 | 轉場數 | 碎裂率 | 誤併率 |
|---|---|---|---|
| **正常轉場** | 4887 | **5.1%** | 4.4% |
| 中途逗留 | 833 | **76.5%** | 9.0% |
| 繞路 | 429 | **90.4%** | 5.4% |
| M4 斷軌 | 319 | **89.0%** | 11.0% |

**碎裂組成:逗留 41%、繞路 25%、M4 斷軌 18%、正常轉場只佔 16%。**

正常轉場的碎裂率 5.1% **剛好落在預算(5%)邊界上**。也就是說架構在它自己的
假設成立時勉強可用 —— 但 **84% 的碎裂來自三個架構根本沒建模**的東西,調 σ 修不好:

1. **繞路**:`transit_llr` 對沒有連結的鏡頭對直接回 `NEG_INF`。走了拓撲沒畫的路 → 100% 開新 chef_id。
2. **逗留**:逗留混合模型寫在 config 裡,但 LLR 門檻仍把超過約 10 秒的擋掉。**模型承認逗留存在,門檻不承認。**
3. **M4 斷軌**:`transit_llr` 第一行就 `cam_from == cam_to → 拒絕`。同鏡頭斷軌後重新出現**必定**開新 chef_id。

### 6.3 兩種失效有不同的驅動因子(失配掃描)

| 廚師人數 | 2 | 3 | 4 | 5 | 6 | 8 |
|---|---|---|---|---|---|---|
| 碎裂率 | 25.9% | 23.6% | 24.8% | 23.3% | 24.2% | 24.3% |
| **誤併率** | **1.9%** | 3.3% | 5.1% | 6.6% | 9.0% | **11.0%** |

**碎裂率與人數幾乎無關,誤併率隨人數單調上升。** 兩者的驅動因子不同:

- **碎裂 ← 結構缺口**(逗留 / 繞路 / M4 斷軌),與現場有幾個人無關
- **誤併 ← 人群密度**(時間窗內的候選數),與結構缺口無關

所以兩者要分開修:補結構缺口降碎裂,收緊門檻或加強外觀降誤併。
把兩者加總成單一「錯誤率」會同時掩蓋這兩條路徑。

其餘維度都是單調退化(逗留 0→50% 使碎裂 15.4%→47.6%;繞路 0→30% 使
19.8%→47.7%;轉場中位數失配 2 倍使 24.8%→54.9%;M4 斷軌率 0→30% 使
21.1%→37.9%),沒有意外的非單調行為。

### 6.4 外觀真的完全不重要(實證)

| 同制服退化 γ | IDF1 | 碎裂率 | 誤併率 |
|---|---|---|---|
| 0.0(EPFL 實測可分性) | 0.141 | **24.8%** | 5.1% |
| 0.5 | 0.140 | **24.8%** | 5.3% |
| 0.9 | 0.139 | **24.8%** | 5.5% |
| 1.0(外觀完全無資訊) | 0.139 | **24.8%** | 5.6% |

**把外觀從實測水準一路降到零,碎裂率一個小數點都沒動**,誤併率只從 5.1% 升到 5.6%。

這實證確認了解析式 §2 的預測(典型情境 E[假候選] = 0.14,絕大多數決策只有一個
候選,外觀根本沒被用到),並直接回答 Phase 4:**投資 NVIDIA TAO 或自訓 OSNet,
在這個架構下買到的東西接近零**。那些法務風險與訓練工程可以省下,
除非架構改成外觀主導。

## 9. 誠實限制

1. **世界參數是估計值,不是量測。** `p_loiter=15%`、`p_detour=5%`、
   `m4_fragment_rate=5%` 都是設定的。所以「結構缺口主導碎裂」這個**定性結論穩健**
   (三個缺口的碎裂率 76~90%,不管比例多少都會主導),但 **41/25/18/16 的分帳比例
   不可信** —— 它直接由那三個估計值決定。要定量得先量業主現場的逗留率與繞路率。
   `src/m5_sim/world.py` 的 `m4_defect_rates()` 已預留讀實跑軌跡的介面,但本輪
   用的是預設估計值(輸出會標明「估計值(未實測)」)。
2. **沒有做預先登記。** 計畫要求在跑之前 commit sweep 網格與判準,實際上直接跑了。
   事後補寫沒有意義,故不補。這代表本輪的參數選擇沒有「事前承諾」的保護,
   下一輪修完架構後重跑時應先登記。
3. **外觀分布仍帶 EPFL 的 session confound**(身份 = 錄影場次),
   所以 same/diff 的可分性偏樂觀。但因為 §6.3 顯示外觀幾乎不影響結果,
   這個偏差對本輪結論的影響很小。
4. **`estimate_clock_skew` 只有單元層級驗證**,沒有用真實共視資料跑過。
5. **仍然沒有端到端跑過真實影片。** `scripts/m5_track_video.py` 尚未建立,
   M4→M5 的接線只有合成驗證。
6. **IDF1 是事件層(把偵測視為完美)**,不含 M3/M4 的偵測誤差。這是刻意的
   —— 為了把 M5 的貢獻從上游誤差裡隔離出來 —— 但不能當成端到端數字。
