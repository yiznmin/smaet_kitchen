## 1. 為什麼從層 0 開始

2026-09-13 的根因分解指出:F1/F2/F4/F5/P1/P2 六個 M5 修法**全部落在層 3/層 4**,
那兩層只佔可歸因失敗的 **11.7%**。遠端訂下的規矩第 3 條是「由下而上修」。

管線順序是 **M3 偵測 → M4 追蹤 → M5 跨鏡頭身份**。本輪處理最上游的「偵測 → 追蹤」。

依規矩第 1 條,**先說打哪一層、那一層佔多少 %** —— 見 §2。

## 3. 三個已在程式碼確認的結構問題

### 3.1 BYTE 的低分救回機制從未作用

- 網格固定 `thr=0.3`(`run_m4m5_chirla_grid.py:93`),偵測在 `model.predict(threshold=0.3)` 就被過濾
- supervision 0.28 ByteTrack 的分數帶(`core.py`):
  · 高分:`score > track_activation_threshold`(0.25)→ 第一輪關聯,IoU > 0.2
  · **低分:0.1 < score < 0.25 → 第二輪關聯,寫死 IoU > 0.5** ← 就是 BYTE
  · **開新 track:score ≥ det_thresh = 0.35**
- 進 tracker 的偵測全部 > 0.3 → **第二輪永遠是空的**

### 3.2 tracker 以 stride 5 被餵資料

`m5_track_video.py:298` 替 M5 把 fps 除以 stride,建 tracker 時沒有。
tracker 實際只看 6 fps,兩次更新之間人移動 5 倍距離。

### 3.3 removed 事件被佔位 id 灌水(已修,`36c97e1`)

7,779 次 removed 裡 4,192 次是 `track_id=-1`(從未啟動的偵測)。
**不影響本輪任何判準**(A/B/C 與 track 數都不用 removed 次數),記錄在此以免誤用舊數字。

## 4. 執行網格(定死)

**一次只改一個因素;緩衝固定 5 秒**(supervision 的緩衝是更新次數,換 stride 必須換算,
`eval_m4_chirla.py` 自動換算並斷言)。

| 格 | 門檻 | stride | 緩衝(次數) | 問的問題 |
|---|---|---|---|---|
| `base` | 0.30 | 5 | 30 | 回歸:必須重現 9/4 的 `coco_none`(見 V1) |
| `t025` | **0.25** | 5 | 30 | 只多收 0.25~0.30 的**高分**框,**沒有**低分帶 |
| `t010` | **0.10** | 5 | 30 | 再加上 0.10~0.25 的**低分帶** → `t010 − t025` = **BYTE 的效果** |
| `s1` | 0.30 | **1** | **150** | stride 效應 |
| `t010_s1` | 0.10 | 1 | 150 | 兩者一起 |

### ⚠ 為什麼比計畫多一格 `t025`

計畫原本只有 `low`(門檻 0.1)。但從 0.3 降到 0.1 同時改了兩件事:
多收 0.25~0.30 的高分框(進第一輪)**與**啟用 0.10~0.25 的低分帶(進第二輪)。
只跑 0.1 分不出 B 的改善來自哪一個。`t025` 把兩者拆開。

偵測器固定為 **RF-DETR nano COCO 預訓**(9/4 主基線)。微調偵測器不在本輪。

## 6. 事先寫下的預測(可被否證)

| # | 預測 | 依據 |
|---|---|---|
| **1** | `t010` 的 B 較 `t025` **下降 ≥ 20%** | BYTE 低分帶正是為了接回被遮擋者;B 的 p25 間隔剛好一個迴圈 |
| **2** | `t025` 的 B 較 `base` 變動 **< 10%** | 多收 0.25~0.30 高分框不是主因 |
| **3** | `t025`、`t010` 的**誤偵 track 數**較 `base` **不增加** | 加進來的框分數都 < 0.35,**只能延長既有 track、不能開新 track** |
| **4** | `t010` 的**身份混雜 track** 較 `base` **增加** | 用低分框延長 track,容易漂到旁邊的人或物件上 |
| **5** | `s1` 的 B 較 `base` **下降 ≥ 20%** | 更新間隔縮短 5 倍,IoU 匹配更容易成功 |
| **6** | `s1` 的**誤偵 track 數**較 `base` **增加** | 未確認的 track 要連續兩次更新才啟動;stride 1 時那只要 67ms,短暫的誤偵更容易被確認 |
| **7** | **C 類次數在所有格變動 < 10%** —— **負對照** | C 是人走出畫面 >5 秒後回來,與追蹤參數無關。**大幅變動表示指標或分類有問題,先查再解讀** |

⚠ 預測 3 與 6 若同時成立,表示「降門檻」與「降 stride」對層 1 的影響方向**相反**,
兩者不能無腦疊加 —— 那正是 `t010_s1` 這一格要回答的。

### 6.1 本輪特有的失敗條件

若 **`t010` 與 `s1` 的 B 下降都 < 10%**,判定為
**「B 不是關聯參數造成的,而是偵測器在遮擋期間根本沒有輸出框」**。

處置先寫死:**不再調 tracker 參數**,改量「B 的間隔期間,該真人在那台鏡頭有 GT 框卻沒有任何偵測」
的比例(需要逐幀 GT 與快取,工具已具備),把問題移回 M3。

   本輪不掃。
