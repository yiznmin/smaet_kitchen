# 預先登記:同鏡頭互斥(F2)對照格 —— 交付資料上的實際差別(2026-09-18)

> **本文件在跑這一格之前定稿並提交 git。** 跑完只追加 §8,§1–§7 不得修改。
> ⚠ 本輪**不是修法**,是對照:使用者問「為什麼沒有『同一時間一個編號只能給一個人』這條規則」,
> 本格把它打開跑一次,量出實際代價,供使用者決定交付時要不要開。

---

## 1. 為什麼跑這一格

使用者 2026-09-18 指出:系統沒有「同一時間一個編號只能給一個人」的限制,
所以編號會像滾雪球一樣被越來越多人共用。

查證結果(本機,唯讀):

| 事實 | 證據 |
|---|---|
| 規則**寫過**,叫 F2 `same_camera_exclusive`,**預設關閉** | `spatiotemporal.py:93`;交付用的 `configs/fix_grid/base.yaml` 與 `camera_topology.chirla.yaml` **都沒有這個鍵** → 走預設 False |
| 交付這批資料**實際違反 2,056 次** | 七個測試序列 `run_meta.resident_final.same_cam_conflicts`:seq_020 648、seq_004 374、seq_025 362、seq_026 317、seq_024 301、seq_006 29、seq_007 25 |
| 全域一對一指派(匈牙利)**從未執行** | 同上 `revotes = 0`、`revote_resolved = 0`(七個序列全部);它只掛在重新投票路徑上,而該路徑預設關閉 |
| 就算打開,匈牙利也**只做一台鏡頭之內**的一對一 | `identity_st.resolve_frame(camera_id)`;跨鏡頭同一時刻從來沒有一對一約束 |
| F2 **只擋同一台鏡頭** | `_score_candidates` 的 F2 檢查是 `any(c == camera_id for c, _t in own)` |
| **少數編號吃掉絕大多數綁定** | `diag_chef_sharing.py`(本機 2026-09-18,`results/levels/chef_sharing_base.json`):987 個編號裡只有 **48 個(4.9%)** 對到 ≥2 個真人,但它們吃掉 **70.5%** 的綁定(2,309 / 3,273);單一編號**最多對到 13 個不同真人**(seq_020 的 chef 84 / 7 / 65 各自都是同一組 13 人) |
| **近三成編號只因誤偵而存在** | 同上:**294 / 987(29.8%)** 只對到誤偵 track,沒有對到任何真人 |

⚠ 上面兩列是**本格的對照基準**(F2 關)。預測 6 要比的就是「最多對到 13 個真人」這個值。

2026-09-12 在**舊追蹤器(bytetrack)**上量過一次(`docs/M5_修復_預先登記_20260905.md` §8.2):

| 格 | 誤併率 | 碎裂率 | 正確率 | IDF1 |
|---|---|---|---|---|
| `base` | 58.84% | 31.33% | **9.83%** | 0.1214 |
| `f2` | 50.51% | 45.63% | **3.86%** | 0.0349 |

⚠ 那一輪的追蹤器與本次交付(`rf_cbiou`)**不同**,數字不可直接套用 → 所以要在交付這批資料上重跑一次。

## 3. 執行網格(定死)

**一格,單一變因。** 除拓撲外,所有參數與 9/15 的 `m5_cbiou` 逐字相同
(`rf_cbiou` @ thr 0.10、7 台、stride 5、`--embedder none`、同一份偵測快取、同一份 `track_gt`)。

| 格 | 拓撲 | 同鏡頭互斥 |
|---|---|---|
| `m5_cbiou`(基線,**不重跑**) | `configs/fix_grid/base.yaml` | 關 |
| `m5_cbiou_f2`(本格) | `configs/fix_grid/f2.yaml` | **開** |

⚠ **評估端一律用 `base.yaml`**(兩格都是)。`eval_levels` / `eval_m4m5_chirla` 只用拓撲的
`overlapping` 做路徑分類,而兩份的 `overlapping` 相同 —— 評估端保持不變,差異才全部來自系統端。

## 4. 判準(本輪只定「量什麼」,不定「要達到多少」)

使用者要看的是**代價**,不是通過與否。要報的:

| 指標 | 為什麼 |
|---|---|
| `same_cam_conflicts` | 機制有沒有生效 |
| 誤併率 / 碎裂率 / 正確率 / IDF1(七序列彙總) | 打開的整體代價 |
| **一個編號對到幾個不同真人**(分布、最大值、前五名) | 直接對應使用者說的「滾雪球」 |
| B 套 L1 / L2 / L3 分級指標 | 交付要報的那張表會變成什麼樣 |
| 誤偵綁定率 | F2 可能把誤偵推去綁別的 chef |

## 5. 事先寫下的預測(可被否證)

| # | 預測 | 依據 |
|---|---|---|
| 1 | `same_cam_conflicts` = **0** | 9/12 的 V2 驗收在兩格都達成 0;不為 0 就是實作壞了,本格作廢 |
| 2 | **B 套 L1 / L2 的單鏡頭 IDF1 逐位不變** | 那是從 `track_id` 與框算的,**M5 從不回饋 M4**。若變了,表示有東西串錯 |
| 3 | 誤併率較基線(59.54%)**下降 ≥ 5pp** | 9/12 降 8.33pp |
| 4 | 碎裂率較基線(30.46%)**上升 ≥ 10pp** | 9/12 升 14.30pp |
| 5 | 正確率較基線(10.00%)**下降** | 9/12 從 9.83% 掉到 3.86% |
| 6 | **「一個編號對到多個真人」的情況不會消失**,最大值下降 < 50% | 互斥管的是**同一瞬間**;chef 21 那 9 個人是**跨時間**累積的,互斥擋不到 |

⚠ **預測 6 是本輪最重要的一條** —— 它直接檢驗使用者的因果假設。
若最大值大幅下降,表示我判斷錯了,互斥確實是滾雪球的主因。

### 5.1 這一格不會回答什麼

1. **不會讓系統變好。** 依 9/12,它是把靜默的誤併換成看得見的碎裂。
2. **不涵蓋跨鏡頭同一時刻的一對一** —— 那需要全域指派,不在本格範圍。
3. 不改任何既有結果:基線不重跑,交付的 A/B 兩套數字不變。

---

## 6. 已知限制

1. 9/12 的數字來自**不同追蹤器**,只能當方向參考,不能當預期值。
2. 「一個編號對到幾個真人」用的是 `track_gt`(整段多數決),與 `diag_chef_label_check.py` 的
   **逐幀 IoU** 判定不同口徑,兩者數字不會一樣,**不可混用**。
3. CHIRLA 是辦公室、每個人衣服不同;廚房是口罩 + 同款制服 → 這裡的代價是下界。
