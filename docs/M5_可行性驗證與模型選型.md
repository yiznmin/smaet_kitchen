> 目的:①用公開資料驗證「外觀 Re-ID 在真實影像上可行、我們的 chef_id 綁定邏輯正確」;
> ②定出**可商用的外觀模型**。承接 [M5_身份管理設計與驗證.md](M5_身份管理設計與驗證.md)(邏輯層已驗證)。

## 1. 可商用模型結論:DINOv2(Apache-2.0)

| 模型 | 程式碼 | 權重 | 可出貨? | 角色 |
|---|---|---|---|---|
| **DINOv2** | Apache-2.0 | **Apache-2.0** | ✅ **可** | **出貨候選**(通用外觀特徵) |
| OSNet / torchreid | MIT | 研究限定(Market-1501…) | ❌ | **僅驗證上限對照** |
| InsightFace(人臉) | MIT | 多非商用 + 生物辨識 | ❌ | 本專案不做 |

- **DINOv2 主模型 code + weights 皆 Apache-2.0**(已查官方 repo;CC-BY-NC 只適用其 Cell-DINO 生物延伸)。影像相似度優於 CLIP;RF-DETR 本就用 DINOv2 backbone → 生態相容。
- DINOv2 是**通用視覺特徵、非 Re-ID 專用**;實際 Re-ID 準確度**要驗**(見下)。
- 來源:https://github.com/facebookresearch/dinov2 (LICENSE: Apache-2.0)

> ⚠ **驗證用的 OSNet 權重與 Market-1501 皆研究限定,不可出貨、不可散布、不可拿來訓練出貨模型。** 它們只用來「證明技術可行 + 當 DINOv2 的對照上限」。

## 2. 主驗證:EPFL 同步多視角(廚房域,推薦)

**為什麼改用 EPFL**(取代 Market-1501 為主):
- Market-1501 是**街上行人、衣著多樣(好認)**;廚房廚師**衣服基本相同**,街上高分不代表廚房。
- EPFL 是**同步多視角**:同一時刻 9 台鏡頭拍**同一個人** → **天生的 same-person ground truth**,而且**就是廚房域**。不同場次(不同參與者)= 不同身份。

**工具**:`scripts/prep_m5_epfl.py`(下載 K 個不同參與者場次、抽同步幀)+ `scripts/reid_eval_epfl.py`(RF-DETR 微調權重偵測 person→裁切→DINOv2 抽特徵→三指標)。
```bash
python scripts/prep_m5_epfl.py --k 6                 # 準備 6 個廚房身份的同步幀
python scripts/reid_eval_epfl.py --embedder dinov2   # 跨視角一致性 + Rank-1 + chef_id 綁定
```
量三件事:①**跨視角一致性**(同人不同視角特徵多像)②**身份判別 Rank-1/mAP**(over 場次)③**chef_id 綁定**掃門檻。

**現況**:管線已在本機(CPU)跑通;用 M3 微調權重偵測 person(COCO 預訓在俯視視角幾乎抓不到人)。
**早期煙霧測試(僅 2 身份)**:DINOv2 跨視角同人相似度 ~0.52、不同人 ~0.45(**差距很小**);2 身份 Rank-1=1.0(身份太少、判別很鬆)。→ **需 6–8 身份才有判別力訊號**。

> ⚠ 觀察到:EPFL 參與者穿**自己的衣服(有色差)**,所以它仍**無法完全代表「制服完全相同」**的極難情形;但域對、且驗到跨視角一致性,遠比 Market-1501 貼近。

## 補充驗證:Market-1501(多身份,但域不同)

```bash
# 需 torch(dinov2)或 torchreid(osnet)+ Market-1501(研究用途)
python scripts/reid_eval_market1501.py --data data/market1501 --embedder dinov2   # 可商用候選
python scripts/reid_eval_market1501.py --data data/market1501 --embedder osnet    # 研究上限對照
```

量三件事:
1. **標準 Re-ID 指標 Rank-1 / mAP**(query 對 gallery 餘弦排名,標準協定排除同 pid+同 cam)。
2. **chef_id 綁定正確率**:模擬 `IdentityManager` 決策(比對最相似的已知廚師、cosine≥門檻才綁),量綁對 / 綁錯(身份污染)/ 漏綁。
3. **掃 `similarity_threshold`** → 定 DINOv2 版操作點,寫回 `configs/reid.yaml`(預估 0.6~0.75)。

- 可插拔 embedder:`src/m5_reid/dino_embedder.py`(DINOv2)、`osnet_embedder.py`(OSNet);皆 `BaseEmbedder` 子類,`IdentityManager` 不動。
- metric/binding 為純函式,已用**合成特徵單測通過**(完美可分離 → rank1=mAP=1.0;門檻行為正確)。

## 3. 結果(EPFL 6 身份,2026-08-12,DINOv2)

6 個不同參與者(廚房身份)× 5 視角 × 15 時刻,RF-DETR 微調權重偵測 person → 449 crops → DINOv2 特徵。

| 指標 | DINOv2 | 白話 |
|---|---|---|
| 跨視角:同人 / 不同人 平均相似度 | 0.490 / 0.465(**差距 0.025**) | 同人 vs 不同人幾乎一樣像 |
| **Rank-1 / Rank-5 / mAP** | **0.111** / 0.327 / 0.159 | 隨機猜 6 人 ~0.17 → **比隨機還差** |
| chef_id 綁定(平均特徵,門檻 0.3) | 綁對 0.79 / **誤併 0.21** | 靠多張平均勉強 79%,但 21% 綁到錯人 |
| OSNet(Re-ID 專用對照) | _跑中/待填_ | 判斷是「域的問題」還是「DINOv2 的問題」 |

**判定:純外觀 Re-ID(至少 DINOv2)在俯視廚房域判別力不足。**
- ⚠ 這 6 位參與者**穿不同衣服**(非統一制服),DINOv2 卻仍分不出 → **連不同衣服都認不準,相同制服只會更慘**。
- 主因(推測):俯視角 + 動作模糊 + crop 含背景;DINOv2 是通用特徵、**沒為認人訓練**。
- → **M5 不應只靠外觀**(見 §7 空間+時序改向)。

> 綁定「平均 79%」看似不低,但那是 6 類 + 重度平均去噪的結果,且 21% 誤併對「食安追責」太高;單張 Rank-1 僅 11% 才是真實判別力。

## 4. 誠實限制(必讀)

1. **街上 ≠ 廚房**:Market-1501 是路上行人、**衣著多樣(較好認)**;廚房廚師**相似白制服(難認)**。這裡拿高分只證明「技術可行」,**不保證廚房**。
2. **驗證資料/OSNet 權重不可出貨**;可出貨路徑只有 **DINOv2** 或**自訓**。
3. **最終仍需自錄多人廚房資料**(2–3 位、實際制服、跨鏡頭、含離開再現、標 chef_id+鏡頭+時間;spec §C.5)才算真正驗證廚房可行性。

---

## 5. 若 DINOv2 不夠用 → 自訓路徑

1. 用**自錄廚房多人資料**(或可商用授權資料)**微調**一個外觀模型(OSNet/DINOv2 架構皆可,重點是**訓練資料可商用**)。
2. 微調後同樣用本工具在自錄 test 集上量 Rank-1/綁定正確率。
3. 換入 `BaseEmbedder` 子類,`IdentityManager` 與門檻流程完全沿用。

## 7. M5 改向:空間+時序為主、外觀為輔(因 §3 純外觀不足)

§3 驗證顯示**純外觀認人不可靠**(Rank-1 11%)。→ M5 設計改成**以空間+時序為主訊號**,外觀只當加分/破平手。

### 兩種相機情境,兩種主要方法
| 情境 | 主要關聯方法 | 說明 |
|---|---|---|
| **重疊同步**(多台同時看同一區,像 EPFL) | **幾何**:同一時刻、同一物理位置投影到多鏡頭 → 同一人 | 幾乎不需外觀;需相機標定/重疊區 |
| **不重疊分站**(A 站 / B 站分開) | **時空交接**:track 在 A 站**出口 zone** 消失 → 在 B 站**入口 zone** 於 [t_min, t_max] 內出現 → 同一人 | 靠**相機拓撲圖 + 轉場時間**;外觀當多候選時的破平手 |

### 需要的東西(多數已有)
- **入/出口 zones**:複用既有 `configs/zones.json` + `src/common/zones.py`(原本給 M6/靜態線用)。
- **相機拓撲設定**(新增):`configs/camera_topology.yaml` —— 哪個鏡頭出口接哪個鏡頭入口、典型轉場秒數。
- **M4 事件**:`lost_track`(在出口)/`new_track`(在入口)已具備(見 `docs/M4_追蹤設計與驗證.md`)。
- **IdentityManager 擴充**:比對候選時,先用「時空門」(位置+時間窗)過濾,再(可選)用外觀 cosine 破平手;外觀權重調低。

### 已實作(Camera Link Model,全可商用)✅

依業界標準 **Camera Link Model** 實作,四線索:**相機拓撲 + 轉場時間(高斯窗)+ 移動方向 + 外觀(DINOv2 輔助)**。

- `configs/camera_topology.yaml`:相機入/出口 zone、有向連結 `links`(轉場時間高斯 μ/σ)、`overlapping` 對、`fusion`(w_st/w_app/門檻)。**真實佈署量測後填入**。
- `src/m5_reid/spatiotemporal.py`:`point_in_zone`(cv2)、`which_zone`(腳點判區)、`CameraTopology.transition_gate`(連結+時間窗+高斯 pdf)。
- `src/m5_reid/identity_st.py`:`SpatioTemporalIdentityManager`——`on_track_lost` 記出口(cam/time);`on_new_track` 先用**時空門**縮候選,再 `fused = w_st·st_prob + w_app·外觀cos` 綁定;內部 key=(camera_id, track_id)。
- **融合公式**:`fused = 0.7·時空 + 0.3·外觀`,≥0.35 才綁。時空為主 → 外觀弱也能綁對。

### 合成驗證 `scripts/verify_m5_st.py` ✅ 全 PASS
| 情境 | 結果 |
|---|---|
| S1 同人跨鏡頭、**外觀故意設 0.15(很弱)** | ✅ 時空扛,仍綁同一 chef(fused 0.745) |
| S2 時間超窗 | ✅ 開新 chef |
| S3 無拓撲連結 | ✅ 開新 chef |
| S4 兩候選在窗 | ✅ 外觀破平手(較像者勝) |
| S5 非重疊同時出現 | ✅ 判為不同人(物理約束) |
| S6 重疊相機同時刻 | ✅ 幾何關聯,綁同一 chef |

> **關鍵**:S1 證明「外觀只有 0.15」時,**時空門仍把人綁對** → 呼應「DINOv2 外觀弱(11%)+ 時空為主 = 可用且可商用」。

### 誠實定位(真實數字待自錄)
- **邏輯已實作+合成驗證通過**,但**真實跨站準確率需自錄多人跨站資料**(2–3 人、走動、離開再現、標 chef_id+鏡頭+時間;spec §C.5)。EPFL 重疊同步單人**無法**驗不重疊轉場。
- **相機拓撲 + 轉場時間需真實佈署量測**(config 現為示例)。
- 外觀(DINOv2)降為輔助;**若日後自訓可商用 OSNet**(見 §5),把 `w_app` 調高即可,架構不動。
