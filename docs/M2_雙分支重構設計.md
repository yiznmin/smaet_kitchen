# M2 雙分支重構設計 + M3 模型定案

> 目的:解決現有 M2 全域動態偵測「抓不到小目標」的結構性漏洞,將 M2 重構為雙分支架構;並定案 M3 主偵測器。
> 設計原則:**準確優先於速度**。
> 文件版本 **v2(2026-06-15)**:分支 B 從「老鼠單一目標」擴充為**多目標(老鼠=動態 + 水漬殘渣=靜態)**,分類器改**多類別**。
> 已實作的動態目標機制與驗證見 [M2_雙分支_實作與驗證結果.md](M2_雙分支_實作與驗證結果.md);授權與選型延續 [模型選型評估.md](模型選型評估.md)。

---

## 1. 背景與設計原則

### 1.1 現況問題

現有 M2([src/m2_motion/detector.py](../src/m2_motion/detector.py))為**純 OpenCV 全域 frame-diff**:

```
BGR → 灰階 + 高斯模糊 → cv2.absdiff(與前幀) → 二值化 → dilate
   → 計算「變動像素 / 整張畫面」比例 motion_ratio
   → motion_ratio > min_motion_ratio(預設 0.002) 即 has_motion
   → 動態像素用 xs.min/max、ys.min/max 合併成「單一 bbox」
```

兩個關鍵限制造成小目標漏抓:

1. **全域門檻**:老鼠在 1080p 畫面只佔 ~0.1% 像素,過不了 `min_motion_ratio` → 被當雜訊濾掉、永遠不下傳 M3。
2. **單一合併 bbox**:即使觸發,所有變動被併成一個大框,小老鼠的位置資訊被淹沒,無法單獨裁切。

這直接威脅事件清單中多個事件能否落地——分支 B 是「**通用小/關鍵目標專線**」,要服務兩類事件:

| 事件清單項目 | 目標 | 動態特性 | 偵測模式 |
|---|---|---|---|
| 病媒防治／老鼠追蹤 | 老鼠(小異物、小蟲同理) | **持續移動** | **動態目標**(已完成) |
| 環境設施／潑灑事件、殘渣掉落 | 水漬、油漬、殘渣 | **潑灑瞬間動,落地後靜止** | **靜態目標**(待做) |

> ⚠ **關鍵:這兩類動態特性相反**(老鼠會動、水漬落地後不動),**不能共用同一套偵測邏輯**,但可共用同一個多類別分類器。詳見 §3.2。

### 1.2 設計原則

| 原則 | 說明 |
|---|---|
| **準確優先於速度** | 寧可多花運算,不可漏抓關鍵目標;模型選型、變體大小都以準確度為先 |
| 觸發運算 ≠ 觸發存檔 | 偵測器可常時跑(運算成本),但**只在確認目標時才存檔**(存檔稀有) |
| 授權合規 | 全部 Apache-2.0 / MIT / BSD + ONNX Runtime,延續出貨紀律,排除 AGPL |
| 不綁死模型版本 | 模型以設定檔管理,保留可切換空間 |

## 2. 決策摘要

| 項目 | 決定 | 理由 |
|---|---|---|
| **M2 架構** | 重構成雙分支(分支 A 大事件 / 分支 B 小/關鍵目標專線) | 全域門檻抓不到小目標 |
| **分支 B 範圍** | **通用「小/關鍵目標」專線**:老鼠(動態)+ 水漬殘渣(靜態) | 對應事件清單病媒防治 + 環境設施 |
| **分支 B 偵測模式** | **動態 + 靜態兩種並行**:老鼠走 MOG2 動態線、水漬走參考背景靜態線 | 兩者動態特性相反(§3.2) |
| **分支 B 分類器** | **獨立輕量分類器(MobileNet 系),多類別** | 輸出「老鼠 / 水漬殘渣 / 拒絕(人碎塊、雜訊)」 |
| **M3 主偵測器** | **RF-DETR(rfdetr)** | 準確度王、小物件最強,符合準確優先;取代速度冠軍 D-FINE-N |

## 3. 雙分支架構流程

```
                M1 影格
                  │
                  ▼
        ┌──────── M2(重構)────────┐
        │  灰階 + 模糊 預處理         │
        │  連通元件分析 → 每個 blob   │
        │  各自 bbox + 面積           │
        └──────┬──────────┬──────────┘
               │          │
        面積大 │          │ 面積小
               ▼          ▼
   ┌── 分支 A：大事件 ──┐  ┌──── 分支 B：小/關鍵目標專線 ────┐
   │ 維持現有 frame-diff │  │ ① 背景相減(MOG2/KNN)         │
   │ has_motion = True   │  │    便宜、高召回,定位小前景 blob │
   │      │              │  │       │                        │
   │      ▼              │  │       ▼                        │
   │ 整張(縮放)送 M3    │  │ ② 在 blob 座標「原生解析度裁切」│
   │   = RF-DETR         │  │    小目標被放大 → 不再是小物件   │
   │ 管:人員/潑灑/跨區  │  │       │                        │
   │ ❌ 分支本身不掛模型 │  │       ▼                        │
   └─────────┬──────────┘  │ ③ 輕量分類器(MobileNet)       │
             │             │    確認「是不是目標?」          │
             │             │       │                        │
             │             │   是 ─┴─ 否                     │
             │             │   ▼      ▼                      │
             │             │  存檔   丟棄(蒸氣/光影過不了③) │
             │             └────────┬───────────────────────┘
             ▼                      ▼
            M3(RF-DETR)→ M4 追蹤 → … 事件判斷/KG
```

### 3.1 三個必須記住的觀念

1. **背景相減身兼兩職**:既是「哪裡動了」的觸發,也是「目標在哪」的定位(region proposal)。模型只負責「認身分」,不負責「找位置」。
2. **裁切 = 放大**:小目標在 256×256 裁圖裡佔比變大,從物理上解決「縮放把小物件吃掉」。**不是盲切一堆 tile**,而是只裁背景相減指出的那 0~3 塊。
3. **常時跑 = 運算成本,存檔只在確認時**:分類器 24h 跑只吃算力;目標稀有 → 真正落地的影格極少。誤觸發(蒸氣、光影)過得了前段,但過不了分類器 → 被算了一下、沒被存。

### 3.2 判別主軸:用「動態特性」分三類 ⭐

人、老鼠、水漬在畫面上的動態特性各不相同,**這是分支 B 過濾的核心依據**:

| 目標 | 會動嗎 | 群聚嗎 | 判別 | 去向 |
|---|---|---|---|---|
| **人** | 持續動 | **一堆密集碎塊疊一起** | 動 + 密集群聚 | 分支 A(送 M3 認人) |
| **老鼠** | 持續動 | 孤立 | 動 + 孤立 | 分支 B **動態線** → 分類器 |
| **水漬/殘渣** | **落地後靜止** | 孤立 | 靜止 + 孤立 + 賴著不走 | 分支 B **靜態線** → 分類器 |

> 一句話:**動的靠 MOG2、靜的靠參考背景;人靠「密集」分出來、水漬靠「持續存在」分出來。**

### 3.3 分支 B 的兩種偵測模式(動態 / 靜態)

因為老鼠會動、水漬不動,分支 B 內部要並行兩條偵測線,**最後匯入同一個多類別分類器**:

```
分支 B
├─ 動態線(老鼠):MOG2 背景相減 → 連通元件 → 面積分流
│     → 空間排除(貼人的碎塊)→ 密度排除(密集群聚=人)
│     → 時序持續性(連貫移動才確認)→ 裁切          ✅ 已完成並驗證
│
└─ 靜態線(水漬):與「乾淨基準背景」比對
      → 找「新出現且持續存在(賴著不走)」的靜止區塊
      → 密度排除(一樣砍人的群聚)→ 裁切            ⬜ 待做
                          │
                          ▼
         多類別分類器:老鼠 / 水漬殘渣 / 拒絕 → 確認才存
```

**為什麼水漬不能走動態線**:MOG2 是「適應性背景」,水漬落地靜止後會被當成背景**學進去 → 幾秒後就偵測不到**;而時序持續性要求「連貫移動」,靜止的水漬也過不了。所以水漬要用**參考背景比對**(對照一張乾淨廚房基準),抓「多出來、且持續存在」的靜止塊。OpenCV 已有 `use_reference_frame`(跟固定參考幀比)可作雛形。

> 兩條線**共用**:連通元件切 blob、密度排除(砍人群聚)、裁切放大、多類別分類器。
> 兩條線**不同**:背景模型(MOG2 適應性 vs 參考幀固定)、確認條件(連貫移動 vs 持續靜止)。

## 4. M2 重構技術細節(設計,後續實作)

> 本次只設計,不改 [detector.py](../src/m2_motion/detector.py)。以下為實作階段依據。

### 4.1 改動點

| 現況 | 改為 |
|---|---|
| `xs.min/max` 合併成單一 bbox | `cv2.connectedComponentsWithStats` → **每個 blob 各自 bbox + 面積** |
| 只有全域 `motion_ratio` 門檻 | 依 **blob 面積分流**:大 blob → 分支 A;小 blob → 分支 B |
| 單一 frame-diff | 分支 B 另建 `cv2.createBackgroundSubtractorMOG2`(對靜止背景小前景最敏感);分支 A 維持 frame-diff |

### 4.2 關鍵參數(實作時需依場域調校)

| 參數 | 作用 | 初始建議 |
|---|---|---|
| `large_blob_area` | 大/小 blob 分流門檻(像素面積) | 依鏡頭實測,例如 > 畫面 1% 走分支 A |
| `min_blob_area` | 分支 B 最小 blob(濾雜訊下限) | 寧鬆勿緊,先求不漏老鼠 |
| `crop_size` | 裁切窗邊長 | 256(視老鼠在畫面的典型大小) |
| `max_crops_per_frame` | 每幀最多裁幾塊 | 限制上限,防廚房大忙時 blob 爆量拖垮分類器 |
| MOG2 `history` / `varThreshold` | 背景模型更新速度 / 敏感度 | 依光線穩定度調 |

> ⚠ `max_crops_per_frame` 觸發截斷時必須 log,避免「以為全看了」實際漏看。

## 5. 分支 B 模型選擇:輕量分類器

### 5.1 任務定位(多類別)

前段(動態線/靜態線)已經**定位 + 裁切放大**,所以分支 B 的模型只需做**分類(classification)**,不需偵測。任務是**多類別**:

```
分類器輸出: 老鼠 / 水漬殘渣 / 拒絕(人碎塊、蒸氣、光影、雜訊)
```

動態線與靜態線的裁圖都餵進**同一個分類器**——它看「長相」決定身分,不管這塊是怎麼被定位出來的。越輕越好(任務單純,且觸發稀有)。

### 5.2 模型決定

| 項目 | 決定 |
|---|---|
| 模型族 | **MobileNetV3 / EfficientNet-lite**(Apache-2.0 / BSD,授權乾淨) |
| 部署 | 匯出 ONNX,**與 M3 共用 ONNX Runtime 後端**,不引入新框架 |
| 變體選擇 | **準確優先 → 取較強的輕量變體(MobileNetV3-Large / EfficientNet-lite0+)**;因分支 B 觸發稀有,多一點算力可接受 |

> 為何不沿用 M3 的 RF-DETR / 不上 YOLOX:RF-DETR 是偵測器(較重),分支 B 不需要再做定位;獨立分類器每次推論最省,且任務單純。代價是多一套訓練/部署管線,但換來分支 B 可獨立調校、不拖累 M3。

### 5.3 資料缺口(最大風險)

沒有現成分類器,**模型必須自行訓練**,每個類別都要樣本:
- **老鼠正樣本**:老鼠 crop(各角度、各光線;可含夜間紅外)。
- **水漬正樣本**:地面水漬/油漬/殘渣 crop(不同形狀、反光程度)。
- **拒絕類負樣本**:人碎塊、蒸氣、光影、反光、小蟲等「會過前段但不是目標」的東西。
- 負樣本品質決定誤報率高低,需刻意蒐集(困難負樣本)。

## 6. M3 模型定案:RF-DETR

### 6.1 決定

**M3 主偵測器採用 RF-DETR(rfdetr)**,取代先前速度評估的暫定冠軍 D-FINE-N。

| 比較 | D-FINE-N | **RF-DETR(選定)** |
|---|---|---|
| 定位 | 效率王(17ms/214MB) | **準確度王,小物件(刀具、器具)最強** |
| backbone | — | DINOv2 |
| fine-tuning | 可 | **官方主打 fine-tuning** |
| 符合本案原則 | 速度優先才選 | **準確優先 → 選定** |

### 6.2 變體與限制

- **變體**:準確優先 → 取 **small / medium**(非 nano);最終以標註廚房資料集實測 mAP 決定。
- **授權**:nano–large 為 Apache-2.0(可商用);**XL / 2XL 為 PML 1.0,不可商用,不採用**。
- **微調硬體**:RF-DETR 為 Transformer、較吃 VRAM,**在 RTX 3050 4GB 上微調吃力**(推論還好)→ 微調建議在較大 GPU 上做。

## 9. 驗收方式

- **分支 B 召回**:用含老鼠的測試片段,量測「老鼠出現 → 是否被存下」的召回率(核心指標,不可漏)。
- **存檔量**:確認分支 B 沒有把蒸氣/光影大量存下(誤報率),對照「全域降門檻」應顯著更少。
- **誤報分析**:檢視被分類器放行的非目標 crop,回饋為下一輪困難負樣本。
- **M3 準確度**:在標註廚房資料集量 RF-DETR 各類別 precision / recall / mAP,特別看小物件(刀具)。
- **端到端**:M2 雙分支 → M3 全流程跑通,確認分支 B 不阻塞分支 A 的即時性。
