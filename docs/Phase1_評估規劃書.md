# 智慧廚房影像分析系統 — Phase 1 評估規劃書

> 本文件為**規劃版**:說明「預計要評估的模型」、「評估指標」、以及「M2 如何處理並交給 M3」。
> 不含任何已測得的數據(結果另見結案報告)。

| 項目 | 內容 |
|---|---|
| 階段 | Phase 1:M2 動態偵測 + M3 物件偵測「速度/資源」評估 |
| 架構 | 集中式單主機、純規則邏輯、不引入 LLM/VLM |
| 授權前提 | 模型須可商用(Apache-2.0 等),避開 AGPL;資料僅作 benchmark |

---

## 1. 預計評估的模型

全部為**可商用(Apache-2.0)**的即時物件偵測模型,以官方來源匯出成 ONNX 後評估。

| 家族 | 變體 | backbone 類型 | 原生解析度 | 角色 |
|---|---|---|---|---|
| **D-FINE** | N / S / M | CNN(HGNet) | 640 | 效率取向 |
| **RF-DETR** | nano / small / medium | ViT(DINOv2) | 384 / 512 / 576 | 準確度、小物件(刀、器具) |
| **RT-DETRv2** | r18 / r34 | CNN(ResNet) | 640 | DETR 成熟基線 |

- ❌ **排除**:Ultralytics YOLOv5/8/10/11/12(AGPL)、RF-DETR XL/2XL(PML);皆不可商用出貨。
- 〔視需要〕若目標主機**無 GPU(純 CPU 部署)**,再追加 DAMO-YOLO(含 CPU 變體)評估。
- 公平比較時:所有模型統一輸入解析度(例如 **672×672**,同為 32 與 56 的倍數,各家皆可原生支援)。

## 2. 評估指標

### 2.1 速度 / 資源(本階段主軸,不需標註)

| 指標 | 定義 | 用途 |
|---|---|---|
| 單張推論延遲(mean) | 一次推論平均耗時(ms) | 即時性 |
| 單張推論延遲(p95) | 95 百分位延遲(ms) | 最壞情況、會不會卡頓 |
| 吞吐(throughput) | 每秒可處理影格數(img/s) | 跟不跟得上攝影機 |
| GPU 記憶體峰值 | 推論期間 VRAM 用量(MB) | 能否塞進目標主機、能同時跑幾個 |
| 可支援鏡頭數 | 吞吐 ÷ 目標幀率 | 直接回答「能接幾顆鏡頭」 |

**測試條件(矩陣)**:
- 解析度:統一解析度(公平比較)/ 各模型原生解析度(反映設計點)。
- 批次大小:1 / 4 / 8(模擬多鏡頭同時送入)。
- 量測方法:**暖機數次**(排除初始化)後**計時多次取平均與 p95**;記錄執行主機 GPU 型號與來源。
- 失敗處理:OOM / 不支援的組合明確標記,不略過。

> ⚠ 速度數據必須在**實際部署的目標主機**上才可作選型依據;開發機數據僅供相對比較。

### 2.2 準確度(後續階段,需標註資料)

| 指標 | 說明 |
|---|---|
| precision / recall | 各類別(person、knife、cutting_board…)偵測正確率 |
| mAP | 綜合平均精度(IoU 門檻下) |
| 小物件表現 | 針對刀具、器具等小目標的偵測率 |

> 本階段(EPFL 無 bbox 標註)**不做準確度**;需以標註的廚房資料(Roboflow / 自標)進行。
> **最終選型 = 速度 × 準確度** 的綜合,不能只看速度。

## 3. M2 如何處理,並如何交給 M3

M2 是 M3(高成本 GPU 推論)的「省電守門員」:用極低 CPU 成本判斷畫面有無變動,只有「有動」才把影格交給 M3。

### 3.1 M2 處理流程(純 OpenCV / CPU,不用模型)

```
輸入影格(BGR)
   │
   ├─① 轉灰階(只看亮度變化,不需顏色)
   │
   ├─② 高斯模糊(抑制感光雜訊,避免誤判)
   │
   ├─③ 與「前一幀(或固定參考幀)」做 cv2.absdiff(逐像素相減)
   │
   ├─④ 二值化:差值 > diff_threshold 的像素標記為「有變化」
   │
   ├─⑤ 計算「變化像素佔全畫面比例」motion_ratio
   │
   └─⑥ 判定:
        motion_ratio > min_motion_ratio  → has_motion = True(+ 變化區域 bbox)
        否則                              → has_motion = False
```

- 參數(`diff_threshold`、`min_motion_ratio`、模糊核、比較模式)以設定檔管理,依場域可調、不需重訓。
- 特性:M2 偵測的是「**動作**」而非「**存在**」;站著不動者可能判為無動態,故門檻須依「不可漏掉的事件」校正。

### 3.2 M2 → M3 的交棒

```
                 ┌─ has_motion = False → 丟棄,不送 M3(省下 GPU 推論)
M2 對每一幀判定 ─┤
                 └─ has_motion = True  → 交給 M3:
                        • 送出該影格(可附動態區域 bbox 作 ROI,縮小 M3 處理範圍)
                        • M3 在該影格上做物件偵測(person / knife / cutting_board …)
```

- **守門員效果**:大量靜止 / 無人影格在 M2 就被擋下,不進入昂貴的 M3,顯著降低 GPU 負載。
- **可選 ROI 加速**:把 M2 的動態 bbox 傳給 M3,讓 M3 只看會動的區域,進一步省算力。
- **介面**:M2 輸出 `{has_motion, motion_ratio, bbox}`;為 True 時影格(與可選 ROI)流入 M3,
  M3 輸出每個物件的 `bbox / class / confidence`,再往後續模組(追蹤、事件判斷)。

## 4. 本階段交付

- 可重現、設定檔驅動的工具:M2 動態偵測、M3 速度評估(ONNX + GPU)。
- M3 速度/資源評估表(上述指標 × 模型 × 解析度 × 批次)。
- 後續:準確度評估與目標主機複核,合併後完成最終選型。
