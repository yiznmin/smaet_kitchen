## 1. 打哪一層、佔多少

**層 0 的 B 類**:同一真人、同一鏡頭的相鄰兩條 track,後一條出生時前一條還在 lost 緩衝內。
9/14 `base`:**683 對,佔相鄰配對 31.0%**。A+B 的天花板約佔 M5 被問的 3,736 次的 **26%**;C(56%)不在範圍。

9/14 第一輪留下的三個事實(§8、§8.11):

1. **調門檻與 stride 不改變 B 的佔比** —— 五格 29.9%~32.3%
2. **不是偵測器沒給框** —— B 斷點期間追蹤器看得到的幀,72.4% 有 ≥ 0.30 的正確框
3. **純 IoU 接不回** —— 舊 track 最後真實框 vs 新 track 第一框的 IoU 中位 0.199,< 0.2 佔 50.4%;
   另有 16.9% IoU ≥ 0.5 仍沒接上(疑似跟丟期間卡爾曼漂移,未驗證)

→ 本輪**換配對方法本身**,每個候選對準一個機制:

| 候選 | 方法 | 對準 |
|---|---|---|
| **C-BIoU**(Yang et al., WACV 2023) | 框放大後再算 IoU,專為相鄰幀不重疊的不規則運動設計 | IoU < 0.2 的 50.4% |
| **OC-SORT**(Cao et al., CVPR 2023) | 以最後觀測再配一次(OCR)、重新出現時以虛擬軌跡重跑卡爾曼(ORU) | IoU ≥ 0.5 仍沒接上的 16.9% |

## 2. 實作與已查證的 API 行為

實作:Roboflow **`trackers==2.6.0`**(Apache 2.0,乾淨重寫)。`KitchenTracker` 新增
`rf_botsort` / `rf_cbiou` / `rf_ocsort` 三個 backend;預設仍是 supervision 的 `bytetrack`,既有結果逐位不變(§7)。

2026-09-15 讀 **pip 下載的 2.6.0 wheel 原始碼**確認(⚠ GitHub `release/stable` 分支的 `trackers/core/` 只有
bytetrack / ocsort / sort,與 2.6.0 不同,一律以 wheel 為準):

| 項目 | 事實 | 對本輪的影響 |
|---|---|---|
| 輸出 | `update()` 只回傳本幀配到的偵測(未配到的 id 為 -1),不含只靠預測的 track | 事件改由內部 `tracks` 推導:已發 id 且 `time_since_update == 0` 為 active、其餘在 `tracks` 裡的為 lost、從 `tracks` 消失為 removed |
| C-BIoU 結構 | 繼承 BoT-SORT:第一輪 BIoU×分數 ≥ 0.2(tracked + lost)、第二輪 BIoU ≥ 0.5(只 tracked)、未確認 track ×分數 ≥ 0.3 沒配到就刪 | 與 supervision ByteTrack **同一套流程**,只換 IoU |
| `BIoU(buffer_ratio=0)` | 直接回傳 `sv.box_iou_batch` | `rf_cbiou` 設 0 ≡ `rf_botsort`(verify_m4 S6 逐位驗證) |
| OC-SORT OCR | 未配到的 track 以 `last_observation` 對剩下的偵測再算一次 IoU | — |
| OC-SORT ORU | `tracklet.py` 的 `_freeze()` 在第一次沒配到時存卡爾曼狀態,`_unfreeze()` 重新出現時以線性插值的虛擬觀測重跑更新 | — |
| OC-SORT 分數 | 低於 `high_conf_det_threshold` 的偵測**整批丟掉**,沒有低分帶 | `ocsort` 餵 0.10 等同餵 0.25 |
| OC-SORT 未確認 track | 不刪,留到緩衝到期;id 要連續配到 `minimum_consecutive_frames` 次才輸出,跟丟後重新計數 | adapter 以內部 `tracker_id` 為準:id 已發、本幀有配到就算 active(對 M5 而言人沒換) |
| 時間 | 傳 `timestamp` 時改以秒算緩衝、卡爾曼一步走 經過秒數×frame_rate 幀 | **不傳**(固定步長),與 supervision 每次 update 走一步相同 |
| 卡爾曼狀態 | supervision XYAH;BoT-SORT/C-BIoU XCYCWH(尺度相關雜訊);OC-SORT XCYCSR | 無法逐位對齊 supervision → 需要 `rf_botsort` 當橋樑格 |
| 本機環境 | Python 3.14 不在官方支援;已安裝的 `pydeprecate` 0.7.0 太舊,import 失敗 | 本機以暫存目錄的 trackers + pydeprecate 0.12 測試,**未裝進環境**;遠端 3.11 為準 |

## 5. 事先寫下的預測(可被否證)

| # | 預測 | 依據 |
|---|---|---|
| **1** | `rf_botsort` 的 B 佔比與 `t010` 相差 **< 3pp** | 同一套配對流程與門檻,只差卡爾曼表示與邊界比較 |
| **2** | `cbiou` 的 B 佔比較 `rf_botsort` **相對下降 ≥ 10%** | 寬 w 的兩框中心水平錯開 d 時,IoU = (w−d)/(w+d);放大 0.3 後 d = 0.67w(原 IoU 0.2)的 BIoU 升到約 0.41 |
| **3** | `ocsort` 的 B 佔比較 `rf_botsort` **相對下降 ≥ 10%** | ORU 修正跟丟期間的漂移、OCR 以最後觀測再配 |
| **4** | `cbiou` 剩下的 B 裡,**IoU < 0.2 那段的對數**較 `rf_botsort` **下降 ≥ 25%** | 預測 2 的機制;降的若是別段,表示改善不是框放大造成的 |
| **5** | `ocsort` 剩下的 B 裡,**IoU ≥ 0.5 那段的對數**較 `rf_botsort` **下降 ≥ 30%** | 預測 3 的機制 |
| **6** | `cbiou` 的**身份混雜 track** 多於 `rf_botsort` | 放大後的框更容易蓋到旁邊的人 |
| **7** | `ocsort` 的**召回(全部幀)**低於 `t010` | 它丟掉 < 0.25 的框,而 `t010` 用了 0.10~0.25 的低分帶 |

⚠ **本輪不用 C 類當負對照。** 9/14 §8.6 證明配對總數大幅變動時 C 不是有效負對照,
而換追蹤器會改變碎片數。只報告 C 的數字,不據以判定。

### 5.1 本輪特有的失敗條件

若 **`cbiou` 與 `ocsort` 的 B 佔比較 `rf_botsort` 相對下降都 < 10%**,判定為
**「在 CHIRLA 這種小框多人場景,純運動配對(預設參數)已到極限」**。

處置先寫死:**不再換純運動追蹤器、不在評估集上調它們的參數**。
層 0 剩下的 B 改由 M5 側處理 —— 9/13 根因分解層 2 那 38.6%「track 還在緩衝內」是同一現象的另一面,
下一份預先登記做候選路徑 (c)(讓還掛在 active、但此刻不在畫面裡的 chef 成為候選)。

### 5.2 採用規則

`cbiou`、`ocsort` 中通過全部主判準與硬性約束者為候選;兩者都通過時取 B 佔比較低者,相差 < 1pp 時取混雜 track 較少者。
**勝出者才進步驟 3**(完整 M5 + 四層分解,另寫預先登記),看層 2「track 還在緩衝內」的 38.6% 有沒有縮小。
兩者都不通過但未觸發 §5.1 → 記錄結果,不採用,下一步由使用者決定。

## 6. 已知限制(報告要照抄,放在結論之前)

1. **本輪只評 M4。** 層 0 改善會不會傳到 M5 層 2,要另跑步驟 3
2. **層 0 天花板約 26%。** 本輪做到最好,M5 仍不會達標;C 類 56% 不是 M4 能修的
3. **方法參數全用套件預設。** 否定結果只代表「預設下沒用」,不代表方法本身沒用 —— 但在評估集上調參就是用測試集選模型
4. **`rf_botsort` 與 `bytetrack` 不是同一實作。** 卡爾曼表示與邊界比較不同,這正是設橋樑格的原因
5. **`ocsort` 沒有低分帶**,與另外三格吃的偵測實際上不同(等同門檻 0.25)
6. **IoU 分段是代理量。** 追蹤器實際比的是卡爾曼預測框
7. **A 類分不清是重複框還是 track 漂移**(同 9/14)
8. **CHIRLA 是辦公室不是廚房**
9. `trackers` 要求 **numpy ≥ 2.0.2**;遠端若是 numpy 1.x,pip 會升級,可能影響同一環境的 torch / rfdetr(本輪評估不需要它們,見 §7.2 的處置)

**預測 4 的讀法**:剩下的 B 依 IoU 分段,`rf_botsort` → `cbiou`:

| IoU | `rf_botsort` | `cbiou` | 變動 |
|---|---|---|---|
| < 0.2 | 269(49.6%) | 185(49.9%) | −31.2% |
| 0.2~0.5 | 174 | 116 | −33.3% |
| 0.5~0.8 | 87 | 64 | −26.4% |
| ≥ 0.8 | 12 | 6 | −50.0% |

**各段幾乎等比例下降,< 0.2 的佔比 49.6% → 49.9% 沒變。** §5 寫的「降的若是別段,表示改善不是框放大造成的」——
這裡不是別段,但也**不是集中在 < 0.2 段**。能說的是「框放大讓各重疊段的斷點都減少」,
**不能說「C-BIoU 專門救回了低重疊的斷點」**。(⚠ IoU 分段是代理量,且 `cbiou` 剩下的 B 間隔中位 45 幀、`rf_botsort` 30 幀,兩者組成不同。)
