# M4 多目標追蹤 — 設計與驗證(2026-08-11)

> 把 M3 每幀「無 ID」的偵測串成有 `track_id` 的軌跡(跨幀一致、撐短暫遮擋),
> 輸出新軌跡事件(→M5 抽特徵)、消失軌跡事件(→中央)。是單幀偵測與時間維度事件(M6)之間**不可省略的橋樑**。

---

## 1. 選型與授權

| 項目 | 決定 | 理由 |
|---|---|---|
| 追蹤器 | **ByteTrack**(主) | spec 既定;純運動 **Kalman + IoU + 匈牙利**,對應 spec §M4 演算法;CPU 即時 |
| 實作來源 | `supervision` 的 `sv.ByteTrack` | **MIT,可商用**;直接吃 RF-DETR `predict()` 回傳的 `sv.Detections` |
| 匈牙利解 | `scipy.optimize.linear_sum_assignment` | supervision 內建,**不需 `lap` 依賴** |
| 備援 | BoT-SORT / OC-SORT(未實作) | 同 `BaseTracker.update` 介面,config `backend` 切換 |
| **不含** | 外觀 / Re-ID 特徵 | **屬 M5**;M4 保持純運動 → 授權乾淨、CPU 快 |

> ⚠ **`sv.ByteTrack` 在 supervision 0.30 移除**(遷移到獨立 `trackers` 套件、`update()` 介面)。
> 對策:唯一觸點是 `src/m4_track/tracker.py`;`requirements.txt` 釘 `supervision<0.30`,遷移時只改 wrapper 一處。

---

## 2. 架構

```
M3 每幀偵測(sv.Detections,無 ID)
        │
        ▼
KitchenTracker.update(det, frame_id, ts)     ← src/m4_track/tracker.py
   ├ sv.ByteTrack.update_with_detections()    (只回傳配對上的偵測)
   ├ 從 tracked/lost/removed 內部清單推導狀態與事件
        │
        ▼
TrackerOutput(frame_id, tracks[], events[])
   ├ tracks:  Track(track_id, bbox, class_id, conf, status, start_frame, hits, history)
   └ events:  new_track(→M5) / lost_track(→中央) / removed
```

### 資料模型(`src/m4_track/tracker.py`)
- `TrackStatus`(active/lost/removed)、`Track`、`TrackEvent`、`TrackerOutput`(皆 dataclass,str-Enum 便於序列化)。
- `BaseTracker` 介面 → `KitchenTracker` 實作;`KitchenTracker.from_config(cfg)` 由 yaml 建。

### 事件推導(關鍵)
`update_with_detections` **只回傳有配對上的偵測、不含事件**,故從 ByteTrack 內部清單推:
- `new_track` = 首次進入 active(未在 `_seen_ids`)。
- `lost_track` = 本幀新進 `lost_tracks`(對上幀差集)。
- `removed` = 本幀新進 `removed_tracks`(**對累積清單差集**,避免重複發)。
- active 但本幀未配對的軌跡 → 用 Kalman 預測框 `STrack.tlbr`,class 沿用上次已知。

### 設定(`configs/tracker.yaml`)
`track_activation_threshold` / `minimum_matching_threshold` / `lost_track_buffer`(遮擋恢復幀數) / `frame_rate` / `minimum_consecutive_frames` / `history_len` / `person_only` / `backend`。

## 3. 驗證

### 3.1 合成序列(`scripts/verify_m4.py`,免 rfdetr/GPU)✅ 全通過
| 情境 | 斷言 | 結果 |
|---|---|---|
| S1 單框移動 | 1 個 new_track、id 全程不變 | ✅ |
| **S2 兩框交叉** | 2 個 new_track、交叉後各自延續、**ID-switch == 0** | ✅ |
| S3 遮擋恢復(gap < buffer) | 發 lost_track、復現沿用**同 id** | ✅ |
| S3b 遮擋過久(gap > buffer) | 發 removed、復現為**新 id** | ✅ |

> S2 是 EPFL(單人)給不了的**多目標**檢查,用合成序列補上。

### 3.2 EPFL 實跑(`scripts/m4_track_video.py`)✅ 打通
COCO 預訓 RF-DETR(只追 person)+ ByteTrack 在 `data/epfl/Boutput0.mp4` 上跑:
- 單一廚師維持**同一個 `track_id`**;`new_track` 事件 = 1;輸出 `tracks.json/csv`、`events.json` + 標註幀。
- 追蹤器本身耗時(排除 RF-DETR)遠低於 spec <5ms/幀目標(單人場景;首幀含暖機略高)。

```bash
python scripts/verify_m4.py                              # 合成驗證(現在就能跑)
python scripts/m4_track_video.py --max-frames 300        # EPFL person 追蹤 demo
python scripts/m4_track_video.py --weights "checkpoint_best_regular (4).pth" --max-frames 200  # 追 11 類(可選)
```

## 4. 資料限制(誠實)

- **EPFL 是單人場景 → 多目標 ID-switch 無法用它量化**(spec §C.1、Phase1 評估計畫書行 91 已記)。本輪用 **合成 S2** 當站位。
- **量化指標(IDF1 / MOTA / ID-switch)後續作法**:`scripts/eval_m4_mot.py`(未建)讀 MOT17 gt + 跑 KitchenTracker → `motmetrics`(MIT)評分。`motmetrics` 為新依賴,**列後續、不在本輪**。
- 廚房內真實驗證需**自錄多人**(2–3 位可辨識、跨工作站),標 chef_id + 時間(spec §C.5)。
