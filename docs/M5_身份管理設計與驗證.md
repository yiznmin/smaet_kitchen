# M5 廚師身份管理(Re-ID)— 設計與驗證(2026-08-11)

> 把 M4 的本地 `track_id` 綁定到全域 `chef_id`:由 M4 的 new_track 事件觸發 → 抽外觀特徵 →
> 用餘弦相似度比對「活躍 + 最近消失」的廚師 → 沿用或開新 `chef_id`。輸出 `chef_id` 給 M6。
> **本輪範圍(使用者確認)**:建**身份管理邏輯 + 合成驗證**;外觀模型用**可插拔介面 + 佔位**;**不做人臉**。

---

## 1. 架構

```
M4 new_track 事件(track_id + 人物 crop)
        │
        ▼
IdentityManager.on_new_track()              ← src/m5_reid/identity.py(我方自有邏輯)
   ├ embedder.extract(crop) → 外觀特徵向量   ← src/m5_reid/embedder.py(可插拔)
   ├ 對「active(其他鏡頭仍在)+ gone(最近消失)」算餘弦相似度
   ├ ≥ 門檻 → 綁回既有 chef_id;否則開新 chef_id
        │
        ▼
MatchResult(track_id, chef_id, matched, similarity)   → chef_id 交給 M6
M4 lost 事件 → on_track_lost():無鏡頭再看得到 → 移入 recently_disappeared(保留 TTL)
```

- `IdentityManager`:`active` / `gone(recently_disappeared)` / `track_to_chef` 三個表 + `chef_id` 計數;`tick()` 讓 gone 逾 TTL 永久移除;代表特徵用 EMA 更新;支援**跨鏡頭一人多 track**。
- `BaseEmbedder`:`extract(crop) -> L2-normalized 向量`。換模型只換 embedder,IdentityManager 不動。

## 2. ⚠ 授權分析(M5 最大風險 — 出貨前必須解決)

Re-ID 的**程式碼**大多乾淨,但**預訓權重與訓練資料集幾乎都是研究限定**,踩到跟 CC-NC 一樣的雷。

| 元件 | 程式碼授權 | 權重 / 訓練資料 | 可出貨? |
|---|---|---|---|
| OSNet / torchreid | MIT ✅ | 常見權重訓練於 Market-1501 / MSMT17 / DukeMTMC | ❌ **權重研究限定** |
| FastReID | Apache ✅ | 同上,看權重來源 | ❌(現成權重) |
| InsightFace | MIT ✅ | 常用人臉包非商用;且**人臉=生物辨識** | ❌ + 法遵負擔 |

**Re-ID 資料集授權**(spec §C.1 列的都踩雷):
- **Market-1501 / MARS / CUHK-SYSU**:研究/學術限定 ❌
- **MSMT17**:明文非商用、需學術協議 ❌(最嚴)
- **DukeMTMC**:因**隱私爭議下架** → 視為禁用 ❌(spec 行 206 已警告)

**結論**:**現成 Re-ID 權重不能直接出貨。** 要出貨得走以下其一(列入待辦):
1. 用**可商用授權**的外觀模型/權重(需逐一稽核來源);
2. 用**自蒐/自錄資料自訓**外觀模型(最穩,但要資料);
3. 現階段用**授權乾淨的佔位特徵**(見下)跑通流程,把模型換入延後。

> 這與專案一路避開 AGPL/CC-NC 的紀律一致——**M5 是最容易誤觸的一關**,先在文件標死。

### 人臉辨識:本輪不做(決策)
spec 原設計含 InsightFace 入場人臉辨識。**本輪決定不做人臉**,原因:①人臉權重多非商用;②**生物辨識 → 隱私/同意/GDPR 級法遵負擔**。廚師身份改**只用身體外觀特徵**維持即可;人臉留待法遵與資料同意確認後再議。

## 3. 本輪做了什麼(授權乾淨、可跑通)

- **`src/m5_reid/identity.py`**:`IdentityManager`(gallery/active/gone + 餘弦比對 + chef_id 綁定 + TTL + 跨鏡頭多 track)、`ChefIdentity`、`MatchResult`——**我方自有邏輯,授權無虞**。
- **`src/m5_reid/embedder.py`**:`BaseEmbedder` 介面 + **`ColorHistogramEmbedder`(佔位)**。用 HSV 顏色直方圖當外觀特徵——**純 OpenCV、可商用、能跑通整條流程**;對「衣色不同的人」可分辨。**非最終精度**,待換入授權乾淨的外觀模型。
- **`configs/reid.yaml`**:`similarity_threshold` / `recently_disappeared_ttl` / `embedding_ema` / embedder 選擇。
  > ⚠ 門檻與 embedder 相關:顏色直方圖 ~0.5;換 OSNet 等通常 0.6~0.75,需重調。

## 4. 驗證(`scripts/verify_m5.py`,免真實模型/資料)✅ 全通過

用顏色直方圖 embedder + 合成「不同衣色人物」crop:

| 情境 | 斷言 | 結果 |
|---|---|---|
| S1 同一人離開再現(TTL 內) | 綁回**同一 chef_id**(sim 0.999) | ✅ |
| S2 不同人(不同衣色) | **開新 chef_id**(sim 0.000) | ✅ |
| S3 離開太久(> TTL)再現 | 舊身份過期 → **開新 chef_id** | ✅ |
| S4 跨鏡頭同時出現(同一人兩鏡頭) | 綁到**同一 chef**、該 chef 有兩個 track | ✅ |

```bash
python scripts/verify_m5.py     # 現在就能跑,免 GPU、免 Re-ID 模型、免資料
```

> 這驗證的是**身份綁定邏輯**(離開再現、不同人、跨鏡頭)——不依賴特定外觀模型;換入真實模型後邏輯不變,只是相似度更準。

---

## 5. 資料限制(誠實)

- **EPFL 完全不能驗 M5**(單人、重疊視角、CC-BY-NC;spec §C.2)。
- M5 真正驗證需**自錄多人**(2–3 位可辨識、跨鏡頭非重疊、含「離開再現」),標 **chef_id + 鏡頭 + 起訖時間**(spec §C.5)。
- 量化(跨鏡頭 Re-ID 正確率)需上述自錄資料或**可商用**的公開多人資料。
