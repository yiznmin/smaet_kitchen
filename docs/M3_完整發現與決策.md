# M3 物件偵測 — 完整發現、流程數據與決策

> 一份總報告:把 M3「怎麼選、怎麼設定」的整個探索過程、所有數據、與最終決策邏輯收在一起。
> 環境:RTX 3050 4GB / Python 3.14 / onnxruntime-gpu(速度)+ 原生框架 CPU(準確度)。資料:Roboflow 廚房(CC BY 4.0、未微調)。

---

> ## ⚠ 模型決策狀態(重要,勿混淆)
> - **家族 = RF-DETR** → ✅ **已定案**(準確度最高 + 最耐高解析度;Apache 可商用)。
> - **尺寸變體(nano / small / medium / large)= ⬜ 尚未鎖定**。
> - **鎖定條件**:必須「**微調後 nano vs medium 都實測、比 AP**」才決定——**不可用「未微調的表現」鎖死**。
> - 原因:**微調會洗牌**。未微調時 medium > nano(見 §2.6),但微調後 nano 可能就夠(便宜快),要看實測。
> - 「我們用 RF-DETR」≠「我們用 medium」。目前 nano/medium 都在用,是**拿來比較**的。

## 0. 系統定位(決定一切的前提)

- **集中式單主機、純規則、不引入 LLM/VLM。**
- **用途 = 事後查詢/追溯,非即時警報**(使用者確認)。
  → M3 最佳化目標是 **準確度優先**;速度非硬限制(可用高解析度),但「跑完整批錄影」的**總成本**仍要靠 **M2 動態過濾**壓低。

| 階段 | 做法 | 工具/腳本 |

## 2. 數據總覽

### 2.1 M2 動態偵測
- 觸發率 41.1%、**對 M3 省電 58.9%**、純 CPU **2.5ms/幀(400FPS)**。守門員定位成立。

### 2.2 M3 速度(8 個 Apache 模型,batch=1)
| 模型 | 原生解析度 | 速度·原生 | 速度·公平672 | GPU(MB) |
|---|---|---|---|---|
| rfdetr_nano | 384 | 15.6ms | 43.3ms | 348 |
| dfine_n | 640 | 17.1ms | 17.3ms | 214 |
| dfine_s | 640 | 23.7ms | 25.1ms | 346 |
| rtdetrv2_r18 | 640 | 27.6ms | 29.3ms | 350 |
| rfdetr_small | 512 | 27.7ms | 45.2ms | 346 |
| rfdetr_medium | 576 | 35.8ms | 45.6ms | 602 |
| rtdetrv2_r34 | 640 | 37.0ms | 38.9ms | 346 |
| dfine_m | 640 | 37.1ms | 38.7ms | 346 |

→ **速度:D-FINE 最快最省**;RF-DETR 在高解析度因 ViT backbone 最重。

### 2.3 M3 準確度(Roboflow,未微調)
| 模型 | mAP@50 | mAP@50:95 | knife AP | 小物件 mAP |
|---|---|---|---|---|
| rfdetr_medium | **0.633** | 0.407 | 0.184 | 0.084 |
| rfdetr_nano | 0.625 | 0.404 | **0.209** | 0.080 |
| rfdetr_small | 0.621 | 0.398 | 0.187 | 0.090 |
| dfine_m | 0.600 | 0.387 | 0.194 | 0.067 |
| dfine_s | 0.570 | 0.367 | 0.197 | 0.083 |
| rtdetrv2_r34 | 0.568 | 0.358 | 0.207 | 0.116 |
| rtdetrv2_r18 | 0.548 | 0.352 | 0.177 | 0.103 |
| dfine_n | 0.546 | 0.354 | 0.174 | 0.076 |

→ **準確度:RF-DETR 最準**;但所有模型**小餐具(刀/叉/匙)AP 僅 0.1–0.2**,大家電 ~0.7。

### 2.4 小物件模擬(把物件縮小,knife AP)
| 模型 | s=1.0 | s=0.5 | s=0.25 |
|---|---|---|---|
| rfdetr_nano | 0.209 | 0.180 | **0.024** |
| dfine_n | 0.174 | 0.121 | **0.030** |

→ **物件縮到 1/4,刀幾乎完全偵測不到** → 俯視遠距下現成模型對刀必失效。

### 2.5 解析度回升(s=0.25 小物件,提高輸入解析度,knife AP)
| 模型 | R=384 | R=640 | R=960 | R=1280 |
|---|---|---|---|---|
| rfdetr_nano | 0.024 | 0.085 | 0.134 | **0.153** |
| dfine_n | — | 0.030 | 0.096 | 0.055 |

→ **高解析度能救小物件(rfdetr 約 6×)**;但「救小傷大」、**RF-DETR 比 D-FINE 更耐高解析度**(dfine 在 1280 崩);回升後仍 ~0.15 → **不夠,須微調**。

### 2.6 EPFL 真畫面實跑:nano vs medium 對小物件差很多(未微調)

在 EPFL Boutput0 真畫面上跑(未微調),**同樣門檻下 nano 與 medium 對「刀」差異明顯**:

| 設定 | 前景大刀 | 誤報 | 說明 |
|---|---|---|---|
| **nano @ thr 0.3** | ❌ 漏 | 少(~12框) | 抓不到刀 |
| **medium @ thr 0.3** | ✅ **抓到**(信心 ~0.30) | bottle 過度偵測 | **勉強抓到,但低信心、不穩** |
| **medium @ thr 0.1** | ✅ 抓到 | ~84框(95%垃圾) | 精準崩盤,不可用 |

→ **模型尺寸對小物件影響大**:medium 在正常門檻(0.3)就抓到近距大刀,nano 抓不到。
→ 但 medium 只是「**低信心勉強抓到近的大刀**」,**遠距小刀仍漏**(對應 §2.4 崩到 0.02);且不穩(門檻 0.4 就漏)。
→ **結論**:這證明「變體選擇會顯著影響小物件」,更說明**微調時 nano/medium 都要試、比較**才能鎖定變體。圖:`results/m3_acc/epfl_vis/`。

## 3. 串起來的發現(一條故事線)

1. **速度** → D-FINE 最快;**準確度** → RF-DETR 最準(兩者對調 = 經典取捨)。
2. 但**所有現成模型對小物件(刀)都不夠準**(AP ~0.2)。
3. **把物件縮小**(模擬俯視遠距)→ 刀 AP **崩到 0.02** → 證實真實部署會失效。
4. **提高解析度**能把刀救回(0.02→0.15,約 6×),但**傷大物件**、且 **RF-DETR 比 D-FINE 耐高解析度**。
5. 即便如此,**未微調的天花板仍只有 ~0.15** → 終局解法是**微調**。

## 4. 最後我們怎麼決策

### 4.1 決策準則(因為是「事後查詢」)
1. **準確度 > 速度**(速度只需滿足「跑完整批錄影的總時間/成本可接受」,由 M2 過濾 + 離線批次處理達成)。
2. **小物件(刀)準確度是關鍵指標**(食安事件靠它)。
3. **可用高解析度**(成本負擔得起)。
4. 模型/資料**授權須可商用**(Apache/CC-BY)。

### 4.2 依準則的選擇
| 決策 | 結論 | 依據 |
|---|---|---|
| **模型方向** | **RF-DETR** | 準確度最高 + **最耐高解析度**(高解析度策略下不崩);Apache 可商用 |
| **變體** ⬜ | **尚未鎖定,待微調後 nano vs medium 實測比 AP 才定** | 微調會洗牌(§2.6:未微調 medium>nano,但不可據此鎖死);以設定檔切換 |
| **輸入解析度** | **較高解析度**(實測對小物件有效) | 解析度回升實驗 |
| **必做** | **在目標解析度上微調** | 高解析度+微調才能把刀拉到可部署、又不傷大物件 |
| **前置過濾** | **保留 M2** | 事後批次處理省 58.9%+ 總成本 |
| **D-FINE 的角色** | 備選(若總算力吃緊) | 最快最省,但準確度與高解析度耐受度較弱 |

### 4.3 決策流程圖
```
事後查詢 → 準確度優先
   │
   ├─ 模型:RF-DETR(準 + 耐高解析度)            ← 已由數據支持
   ├─ 解析度:偏高(救小物件)                    ← 已由數據支持
   ├─ 必要條件:用「目標鏡頭視角 + 含刀/砧板/生肉/人」的資料微調   ← 尚缺資料
   └─ 部署:離線批次 + M2 過濾控總成本
```

### 4.4 這個決策「還沒鎖死」的部分(誠實)
- 全部數據在 **RTX 3050、未微調、家用廚房照片** → 方向可信,**絕對數字待目標主機 + 自標資料複核**。
- **最終變體與部署解析度**,要等「微調 + 目標主機」後才定案。
