# M3 速度選型 — 公平比較(統一 672×672,RTX 3050)

| | |
|---|---|
| 環境 | RTX 3050 Laptop 4GB、onnxruntime-gpu 1.26(CUDA)、Python 3.14 |
| 解析度 | **全部統一 672×672**(672 同時是 32 與 56 的倍數,8 模型皆原生可跑,無內插) |
| 量測 | 純速度/資源(**未含準確度**) |
| 數據 | `results/m3/m3_speed_table_fair672.csv` |

> 為何 672:D-FINE/RT-DETR 需 32 倍數、RF-DETR(DINOv2)需 56 倍數;640 對 RF-DETR 不合法。
> RF-DETR 在建構時設 resolution=672(非匯出時 resize),以規避 ONNX 無法匯出的 antialias 內插 op。

## 公平排名(batch=1,同為 672)

| 名次 | 模型 | 延遲 mean/p95 (ms) | 吞吐 (img/s) | GPU (MB) |
|---|---|---|---|---|
| 🥇 | **dfine_n** | 17.3 / 23.2 | **57.9** | **214** |
| 2 | dfine_s | 25.1 / 27.4 | 39.9 | 346 |
| 3 | rtdetrv2_r18 | 29.3 / 31.9 | 34.2 | 354 |
| 4 | dfine_m | 38.7 / 40.7 | 25.9 | 346 |
| 5 | rtdetrv2_r34 | 38.9 / 40.2 | 25.7 | 346 |
| 6 | rfdetr_nano | 43.3 / 44.0 | 23.1 | 602 |
| 7 | rfdetr_small | 45.2 / 46.8 | 22.1 | 600 |
| 8 | rfdetr_medium | 45.6 / 46.3 | 21.9 | 602 |

## 關鍵發現:公平比較推翻了原生尺寸的印象

- 原生尺寸時 **rfdetr_nano 看似最快(384、15.6ms)**;但**統一到 672 後,它變最慢(43ms)**。
- 原因:**RF-DETR 用 DINOv2 ViT backbone,運算量隨解析度二次成長**;D-FINE/RT-DETR 是 CNN backbone,高解析度較省。
- **同條件下 D-FINE 全面領先**:dfine_n 在 672 比 rfdetr_nano **快約 2.5 倍、記憶體少 1/3**。

## 批次與記憶體(多鏡頭)

- D-FINE / RT-DETR 批次可擴:dfine_n batch 1→8 吞吐 57.9 → 98.4 img/s,記憶體 214→1112 MB。
- ⚠ **RF-DETR 在 672 + batch 8 崩潰**:記憶體衝到 ~3.8 GB(逼近 4GB),延遲暴增到 **12 秒**、吞吐掉到 0.6 img/s
  —— 這是**撞到 4GB 記憶體牆後的抖動**,不是正常數字。表示 RF-DETR 在高解析度多批次對 VRAM 需求很大。

---

## 初步結論(僅速度;準確度未測)

> **純速度/資源:D-FINE 系列是同條件下的明確贏家**,dfine_n 兼顧最快與最省記憶體,批次擴展也好。
> RT-DETR-r18 次之。**RF-DETR 在同解析度下最重**(ViT backbone 之故)。

## 但這還不是最終答案 —— 公平比較也有「另一面」

- 本表是「**同解析度的速度**」。RF-DETR 的設計哲學是**在較低解析度(384)就達到高準確度、尤其小物件**;
  強迫它跑 672 是拿它的弱項(高解析度算量)比較。
- 真正要回答的是:「**rfdetr@384 偵測刀具的準確度 vs dfine@640 的準確度**,各自的速度是多少」——
  這是**速度 × 準確度的綜合**,必須加上**有標註的廚房資料做準確度評估**才能定論。
- 因此本「公平速度比較」的正確用法是:**先用它淘汰「同條件下又慢又吃記憶體」的選項**,
  再對速度可接受者做準確度評估。
