# M3 物件偵測 — 速度選型結果(RTX 3050 初步)

| | |
|---|---|
| 執行環境 | **NVIDIA RTX 3050 Laptop 4GB**、onnxruntime-gpu 1.26(CUDA EP)、Python 3.14 |
| 日期 | 2026-05-31 |
| 量測 | 純**速度/資源**(延遲、吞吐、GPU 記憶體);**未含準確度**(EPFL 無 bbox 標註) |
| 原始數據 | `results/m3/m3_speed_table.csv`(每組合一列) |

> ⚠️ **三個必讀前提**
> 1. **3050 非部署主機** → 數字「**相對排名可信、絕對值不可信**」;最終選型須在目標主機複核。
> 2. **這只是速度,不是準確度** → RF-DETR「小物件強」這種優勢在此**量不到**;最終選型要再加準確度(需標註的廚房資料)。
> 3. **各模型原生解析度不同**(RF-DETR 384/512/576、D-FINE/RT-DETR 640)→ 不是純同條件對比;
>    高解析度通常較慢但對小物件(刀、器具)較有利。

| 模型 | 解析度 | 延遲 mean / p95 (ms) | 吞吐 (img/s) | GPU (MB) |
|---|---|---|---|---|
| **rfdetr_nano** | 384 | 15.6 / 16.6 | **64.0** | 348 |
| **dfine_n** | 640 | 17.1 / 22.4 | 58.6 | **214** |
| dfine_s | 640 | 23.7 / 25.8 | 42.2 | 346 |
| rtdetrv2_r18 | 640 | 27.6 / 28.5 | 36.3 | 350 |
| rfdetr_small | 512 | 27.7 / 28.7 | 36.1 | 346 |
| rfdetr_medium | 576 | 35.8 / 37.8 | 27.9 | 602 |
| rtdetrv2_r34 | 640 | 37.0 / 38.1 | 27.0 | 346 |
| dfine_m | 640 | 37.1 / 39.8 | 26.9 | 346 |
| *ssdlite(參考,非候選)* | 320 | 35.6 / 38.3 | 28.1 | 258 |

## 批次對吞吐的提升(多鏡頭同時送)

以 dfine_n 為例:batch 1→4→8 吞吐 58.6 → 99.9 → **106.3 img/s**(GPU 記憶體 214→600→1112 MB)。
→ 批次處理能顯著提升「多鏡頭」總吞吐,代價是單批延遲上升與記憶體增加。所有模型在 4GB 下 batch 8 都跑得動(峰值 ~2.1GB)。

---

## 初步觀察與建議(僅速度面,待準確度與目標主機複核)

1. **效率最佳:D-FINE-N** — 在**完整 640 解析度**下只要 17ms / 58.6fps,且**記憶體最低(214MB)**。
   多鏡頭批次下吞吐可到 106 img/s。對「省資源、接多鏡頭、又要 640 完整解析度」最划算。
2. **rfdetr_nano 雖延遲最低(15.6ms)**,但那是因為它只用 **384 解析度**;廚房要偵測**刀、小器具**,
   低解析度可能吃虧。要公平比較,應把 RF-DETR 拉到 640 再測(RF-DETR 支援設定解析度,列為後續)。
3. **要更高準確度時的次選**:D-FINE-S(24ms)、RT-DETR-r18(28ms)仍在即時範圍。
4. **4GB 不是瓶頸**(本批模型在此尺寸都沒 OOM);真正瓶頸是**延遲/吞吐**。

> 最終建議:**先以 D-FINE-N / D-FINE-S 為主力候選**,RF-DETR 系列待「拉到 640 + 加準確度評估」後再定高下。

## 後續(建議於目標主機進行)
1. 補齊上述三模型(或在目標主機一次處理)。
2. RF-DETR 改用 640 解析度重測,與 D-FINE/RT-DETR 同條件比較。
3. 加上**準確度評估**(用標註的廚房資料)→ 速度+準確度合併才是最終選型依據。
4. 全部在**目標部署主機 GPU** 上重跑,取得可作結論的絕對數字。
