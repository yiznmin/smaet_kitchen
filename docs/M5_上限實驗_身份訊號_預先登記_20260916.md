## 1. 為什麼做

使用者 2026-09-16 提出的設計主張:

> 每次看到人,都能確認一下是誰。這樣就算 M4 追錯,下一次確認也能改回來。
> 前提是每個框裡要有「分辨是誰」的訊號。

現況做不到,而且原因已經查清楚(9/15,三份探索性調查):

| 事實 | 出處 |
|---|---|
| 身份**只在 track 出生時決定一次**,之後不再檢查 | `docs/身份辨識設計檢討_20260915.md` §1–§2 |
| 綁定分數**不含任何「這是誰」的資訊**:2,286 次成功綁定全部來自常數 `3.8063 − ln k`(k = 重疊鏡頭上掛著的身份條目數),**k ≤ 8 必綁、同分任選** | `docs/M5_綁定規則實測_20260915.md` §3.1、§3.3 |
| 轉場路徑理論最高 **1.484 < 門檻 1.6094** → 結構上不可能綁定 | 同上 §3.2 |
| 59 人裡 **27 人第一次出現就被綁到別人身上** | 同上 §3.3 |
| 唯一的「重新檢查」(P1 累積投票)開啟後投 **52,259 票只改判 423 次(0.81%)**,因為 `embedder none` 的外觀向量全零,**每一票的證據與出生時完全相同** | `docs/M5_修復P1_預先登記_20260913.md` §8 |

→ **持續重新確認失敗過一次,但失敗原因是沒有訊號,不是機制不對。**

**本輪要回答的兩個問題**(給定一個準確率 p、每個框都讀得到的身份訊號):

1. 持續重新確認能不能把 M4 造成的錯綁改回來?
2. p 要多高,誤併率才會 ≤ 1%(驗收門檻)?

答案直接決定:方案 A(可辨識標記)的**規格依據**,以及方案 B(位置/時間/路線,8/28 模擬誤併率約 5.6%)夠不夠。

⚠ **打哪一層**:這不打 M4 的任何一層,它改的是 **M5 決定身份的時機與依據**。
層 0/層 1 的改善都已證明傳不到綁定規則本身(`docs/M5_步驟3_追蹤器傳導_預先登記_20260915.md` §8.1、`M5_綁定規則實測` §2)。

### 2.1 訊號怎麼建模(不是拍一個權重)

讀取器每次讀出一個 id,**正確機率 p**,否則從其他 K−1 個 id 均勻誤讀。
比較的是**兩次獨立讀數**(這次的讀數 vs 候選 chef 身上存的上一次讀數):

    P_same = p² + (1−p)²/(K−1)
    P_diff = 2p(1−p)/(K−1) + (K−2)(1−p)²/(K−1)²
    相同 → llr = log(P_same / P_diff);不同 → llr = log((1−P_same)/(1−P_diff))

端點:p=1 → 相同是無限強證據(由 `clip=8.0` 夾住);**p=1/K → llr 恆為 0**(讀數等於亂猜)。

⚠ 刻意**不走** `embedder` / `AppearanceLR`:那條路的高斯參數是為 DINOv2 校正的(d′=0.25),
把合成訊號塞進去會被壓扁,且準確率 p 與假設的鑑別力不一致。

⚠ 存在 chef 身上的是**一次有雜訊的讀數**,不是真值 —— 推導就建立在「兩次讀數比對」上。

## 4. 判準(先寫死)

基準 `m5_cbiou`(7 台):IDF1 **0.1574**、正確率 **10.00%**、誤併率 **59.54%**、碎裂率 **30.46%**、誤偵綁定率 **34.01%**。

## 5. 事先寫下的預測(可被否證)

| # | 預測 | 依據 |
|---|---|---|
| **1** | `cue100_off`:誤併率 ≤ 5%,但**碎裂率較基準上升 ≥ 10pp** | 完美訊號能在候選集裡選對,但 L2(正確的人不在候選集)佔可歸因 40.41% 不會因此消失 → 改成開新身份 |
| **2** | `cue100_on`:誤併率 ≤ 1% 且正確率 ≥ 60% | 重新確認能把出生時的錯改回來 |
| **3** | 每個 p,`on` 的正確率都 ≥ `off` | 使用者主張;不成立表示重新確認機制本身有問題 |
| **4** | 誤併率 ≤ 1% 需要 **p ≥ 0.90** | 59 人中 27 人第一次出現就綁錯;每次誤讀都可能製造一個新的誤併源頭 |
| **5** | `cue060_on` 的誤併率**高於** `cue060_off` | 錯誤訊號被反覆採信,投票會把正確的綁定改掉 |
| **6** | 即使 `cue100_on`,正確率仍 **< 90%** | 投票只能整條 track 換綁、**不能從中間切開**;M4 的混人 track(7 台 389 條)在架構上修不掉 |
| **7** | 探索格 `burst=30` 的誤併率**高於**同 p 的獨立誤讀格 | 連續誤讀會累積成一面倒的票數,而獨立誤讀會被多數決洗掉 |

⚠ **本輪不用 C 類或碎裂率當負對照** —— 訊號本來就會把誤併轉成碎裂(預測 1),方向已被預期。
真正的負對照是 `verify_m5_cue.py`【5】最後一項:**沒有訊號時同一情境不會改判**(本機已通過)。

### 5.1 失敗條件(先寫死)

若 **`cue100_on` 的誤併率仍 > 10%**,判定為
**「持續重新確認 + 整條重綁,不足以修正 M4 的錯誤」**。

處置先寫死:**不進行標記尺寸預研**(訊號再準也沒用),
改為先做「**把 track 從中間切開**」的架構變更,或回到追蹤層;結果回報使用者決定。

### 5.2 採用規則

本輪**不改任何預設值**。`fusion.cue` 與 `--oracle-cue` 是實驗設施,不是可出貨的功能
(真實系統要的是真的讀取器,不是從真值合成的訊號)。

## 6. 已知限制(報告要照抄,放在結論之前)

1. **這是上限,不是可達成的效能。** 訊號從真值合成,真實讀取器還有延遲、角度、遮擋、解析度問題
2. **誤讀是獨立抽樣的**(除了探索格);真實標記被遮住時錯誤成群
3. **投票不能切開混人的 track**,`_rebind` 只能整條搬家 → 預測 6 量的就是這個天花板
4. **重新確認只能綁到已存在的 chef**,不會開新身份
5. **真值進入決策** —— 這一格的數字**不可與正式評估並列**,只能用來回答「上限是多少」
6. CHIRLA 是辦公室、每個人衣服不同;**廚房是口罩 + 同款制服 + 斜角鏡頭**(使用者確認)
7. 7 台含 camera_5、6(玻璃倒影誤偵的大宗);排除它們會失去全部三條轉場連結
8. 常數綁定規則來自**沒有地面校正**的設定;有地面校正時重疊路徑會換成 `GroundPlaneLR`,本輪結論不自動成立
9. `clip=8.0` 決定了訊號的發言權上限,**沒有掃過** —— p=1 時相同讀數固定給 +8 nats
