# M5 綁不對身份的根因分解(2026-09-13)

> 這份不是預先登記,是**診斷**。方法是把既有產出重新歸因,加上一次不改變任何
> 決策的重跑(V1 已驗:`tracks.csv` / `track_events.csv` 逐位相同)。
> 修法本身另寫預先登記。

---

## 1. 為什麼做這件事

9/12 與 9/13 兩輪、六個修法(F1 margin、F2 同鏡頭互斥、F4 跨鏡頭位置、
F5 轉場地點、P1 累積投票、P2 Hungarian)**沒有一個提升 IDF1**。
每一輪的流程都是「猜一個原因 → 實作 → 跑網格 → 沒用」。

問題出在我們從來沒量過**一次綁定決策到底敗在哪一層**。彙總指標
(誤併 58.23% / 碎裂 31.33% / 正確 10.44%)區分不了四種處方完全不同的失敗:

| 層 | 失敗樣態 | 若主因在此,處方是 |
|---|---|---|
| **L1 偵測** | 綁到誤偵 track(根本不是人) | 靜止/非人過濾 |
| **L2 候選集** | 正確答案**不在**候選集裡 | 候選集生成 / 拓撲 / 狀態機 |
| **L3 評分** | 在候選集裡但沒排第一 | 補證據(外觀模型) |
| **L4 門檻** | 排第一但沒過門檻 → 開新身份 | 門檻校準 |

**六個修法全部作用在 L3 與 L4。**

## 2. ⚠ 先修掉一個指標 bug:跨序列撞號

`eval_m4m5_chirla.py` 的 `build_records` 用原始 int `gt_id` / `chef_id`,
而 main 把七個序列的 records 直接累加 —— 但 CHIRLA **每個序列的 `gt_id` 都從 1 開始**,
`chef_id` 也是(每個序列是獨立 process,`_next` 從 1 起算)。
於是 seq_004 的 1 號與 seq_020 的 1 號被當成同一個人。

處置:在 `build_records` 把兩個 id 都加上 `"<seq>:"` 前綴。

| 指標 | 報告值 | 修正值 |
|---|---|---|
| `idf1` | 0.1214 | **0.1512** |
| `p_correct` | 0.0983 | 0.1044 |
| `p_false_merge` | 0.5884 | 0.5823 |
| `p_break` | 0.3133 | 0.3133(不變) |
| `n_gt` / `n_pred` | 17 / 296 | **59 / 826** |
| `fragmentation.mean` | 51.94 | **17.22** |

事先寫死的自檢全部通過:`p_break` 完全不變(它不依賴 id 命名空間)、
`p_false_merge` 變動 −0.61pp、誤偵綁定率與 `path_split` 決策數不變。

## 3. 四層分解的做法

三個最小改動,全部預設關閉、關閉時逐位相同:

| 檔案 | 改什麼 |
|---|---|
| `src/m5_reid/identity_st.py` | `on_new_track` 多存一行 `self.last_cands`(候選快照,不影響決策) |
| `scripts/m5_track_video.py` | 新增 `--track-gt <json>`;`chef_events.jsonl` 多寫 `gt_id` / `layer` / `gt_rank` / `top1_*` 等診斷欄位 |
| `scripts/make_track_gt.py`(新) | 直接 import `eval_m4m5_chirla.match_tracks` 產生 `{"<camera>|<track_id>": gt_id}` |

**「正確答案」定義成該真值身份上一次綁到的 `chef_id`**,刻意與
`metrics.binding_outcomes` 判定「正確」的條件一致,否則分解出來的數字對不上指標。

⚠ 用 `base` 那一格算出的真值表可以餵給其他格:`m5_track_video.py` 的 tracker
只吃偵測結果,**M5 從不回饋到 M4**,所以 `(camera, track_id)` 在所有 M5 變體之間逐條相同。

## 4. 結果

### 4.1 四層分解

| 層 | 次數 | 佔全部決策 | 佔可歸因 |
|---|---|---|---|
| **L2 候選集** | **1,012** | 27.1% | **41.1%** |
| L3 評分 | 238 | 6.4% | 9.7% |
| L4 門檻 | 48 | 1.3% | 2.0% |
| OK | 1,163 | 31.1% | 47.3% |
| L1 偵測(不進分母) | 1,216 | 32.5% | — |
| L0 初登場(不進分母) | 59 | 1.6% | — |

**主因是 L2,不是 L3。** 評分層只佔 9.7%,門檻層只佔 2.0%。

### 4.2 交叉核對:層 × 指標結果

| 層 | 正確 | 誤併 | 碎裂 | 合計 |
|---|---|---|---|---|
| OK | 257 | **906** | 0 | 1,163 |
| L2 候選集 | 0 | 331 | **681** | 1,012 |
| L3 評分 | 0 | 196 | 42 | 238 |
| L4 門檻 | 0 | 0 | 48 | 48 |
| **合計** | 257 | 1,433 | 771 | 2,461 |
| | 10.44% | 58.23% | 31.33% | |

兩個讀法:

- **碎裂 771 次裡有 681 次(88.3%)來自 L2** —— 找不到正確答案只好開新身份。
  門檻層只有 48 次,所以**碎裂不是門檻太嚴造成的**。
- **誤併 1,433 次裡有 906 次(63.2%)落在 `OK` 那一列** —— 系統一直穩定地把這個人
  綁到同一個 `chef_id`,但那個 id 的多數票屬於別人。也就是**兩個人早就被併成一個身份**,
  之後每一次「正確地維持現狀」都被記為誤併。錯誤發生在更早,後面只是繼承。

### 4.3 L2 為什麼發生 —— 1,008 / 1,012(99.6%)是同一個原因

> **正確的那位廚師還在 `self.active` 裡,而 `_score_candidates` 的兩條候選路徑都碰不到他。**
>
> - 路徑 (a)(`identity_st.py` 的跨時轉場)只掃 `self.gone` —— 該 chef 必須走完
>   三段式離場(`lost` → `removed` → `_exit`)才會進去
> - 路徑 (b)(重疊幾何)只掃 `self.active`,而且要求
>   `c != camera_id and is_overlapping(c, camera_id)`
>
> 一個「**還被追蹤著、但出現在不重疊的鏡頭上(或同一台鏡頭)**」的人,
> **兩條路徑都不收 —— 候選集裡結構性地沒有正確答案。**

成因細分:

| 成因 | 次數 | 佔 L2 |
|---|---|---|
| **這對鏡頭沒有轉場連結(且不重疊)** | 680 | 67.2% |
| **同一台鏡頭(M4 斷軌)** | 269 | 26.6% |
| 有轉場連結,但時間門擋掉 | 53 | 5.2% |
| TTL 已過期(> 100s) | 7 | 0.7% |
| 重疊鏡頭對,但對方 track 已消失 | 3 | 0.3% |

⚠ **這不是困難的長期重識別問題,是秒級的連續性斷掉:**

- 距離該身份上次被綁定:**中位 1.42 秒**,p75 5.00 秒,p90 12.67 秒
- **74.6% 發生在 5 秒的 `lost_track_buffer` 之內** —— 舊 track 根本還活著,
  chef 還在 `active`,所以連 `gone` 都進不去
- TTL(100 秒)幾乎從來不是問題(0.7%)

### 4.4 拓撲覆蓋率

7 台相機 = 21 個無向對 / 42 個有向對。實際建立的:

| 項目 | 數量 |
|---|---|
| 宣告為重疊 | **7 對** |
| 建立了轉場連結 | **3 個有向對**(2→6、6→7、7→5) |
| **兩者都沒有的無向對** | **11 對** —— 1\|2、1\|3、1\|4、1\|5、1\|6、1\|7、2\|7、3\|6、3\|7、4\|6、4\|7 |

camera_1 與**其他六台全部**沒有任何連結或重疊關係。

## 5. 這解釋了為什麼六個修法全部失效

F1/F2/F4/F5/P1/P2 全部作用在「候選集已經有正確答案之後」的環節 ——
評分、排序、門檻、投票、全域指派。而 **41% 的失敗發生在正確答案根本沒進候選集的時候**,
那些修法在結構上就碰不到主要病灶。

其中兩個還讓情況更糟,而且現在看得出為什麼:

- **F1 margin**:讓系統更常拒絕綁定。碎裂本來就是最大宗(31.33%),
  再加一道拒絕 → 碎裂 92.56%、IDF1 0.0393。
- **F2 同鏡頭互斥**:把「同一台鏡頭上的既有 chef」排除得更徹底,
  而 L2 有 26.6% 正是同鏡頭斷軌 —— 它加深了漏洞。

也解釋了 9/13 的一個觀察:`p1` 投了 52,259 票只改判 423 次(0.81%)。
投票只能在候選集內重排,而正確答案有四成的時候不在裡面。

## 6. 這一輪不能回答什麼

1. **`track_gt` 來自逐幀 IoU 配對 + 多數決**,一條在兩人之間跳的 track 只會拿到一個 gt。
   L2/L3 的分解本身帶 M4 的誤差。
2. **「正確答案」定義成「上一次綁到的 chef_id」** —— 與指標的判準一致,但如果那個
   chef_id 本身早就被污染(見 §4.2 的 906 那格),「找到它」也不等於對。
3. **沒有量 L1 修好之後 L2 會變多少。** 誤偵也會開身份、也會佔候選集,兩層有交互作用。
4. **CHIRLA 標註的負 id 是 distractor**,`load_gt` 用 `abs()` 折成正數 ——
   distractor `-3` 與真人 `3` 被併成同一個身份。本份分解沒有把它們分開。
5. **CHIRLA 是辦公室不是廚房**,絕對值不可當廚房預測值。
6. **這是診斷不是修法。** 「補上漏洞會讓 IDF1 上升多少」還沒有任何證據,
   要另寫預先登記去量。

## 7. 下一步(依證據排序,不是依直覺)

1. **補上候選集的結構性漏洞**(打 L2 的 41.1%)——
   讓仍在 `active` 的 chef 在「同鏡頭」與「非重疊跨鏡頭」情境下也能成為候選,
   用既有的 `SameCameraTransit` 與 `UnknownPathTransit` 評分。
   ⚠ 這會讓候選集變大,必須同時量誤併會不會惡化。
2. **重建拓撲覆蓋**(打 L2 的 67.2%)—— 11 個無向對既不重疊也沒連結,
   而 `chirla_build_topology.py` 只從推導集三個序列估。要查是門檻太嚴還是素材真的不夠。
3. **靜止/非人過濾**(打 L1 的 32.5%)—— 9/3 §6 早就寫死的處置,已觸發兩輪未執行。
   目標是拿到 `ft_none` 的精確度(誤偵 11.7%)又保住 `coco_none` 的召回(88.0%)。
4. **外觀模型**(打 L3 的 9.7%)—— 仍然需要,但**排在第四**,
   而且現在知道它最多只能解 9.7% 的失敗。

# 8. 完整的因果鏈 —— 為什麼一定要從最底層解決

> §1–§7 是分解的方法與結果。這一節把它串成一條因果鏈,並說明
> **為什麼「繼續修最上層」在結構上不可能有效**。
> 這是本輪最重要的結論,報告要照抄。

## 8.1 五層,由下而上

### 層 0 — 問題被問了 43 倍那麼多次

| 事件(七個序列合計) | 次數 |
|---|---|
| `new_track` = M5 被問「這是誰」 | **3,736** |
| `lost_track` | 10,035 |
| `reacquired`(遮擋救回) | 6,382(**63.6%**) |
| `removed`(救不回 → 下次出現是全新 track) | 7,779 |

**一個真人被 M4 切成中位 46 條 track**(平均 42.7,最多 91)。
59 個真值身份產生 2,520 條有真值的 track。

M5 不是「偶爾判斷一次這是不是同一個人」,它被問了 3,736 次,
每一次都有出錯的機會,而錯一次就多一個身份。
**追蹤要成功,首先要少問。**

### 層 1 — 三分之一的問題根本沒有正確答案

1,216 條 track(**32.5%**)是誤偵。它們照樣被綁到廚師身上(883 次綁定,佔 34.0%),
污染那位廚師的外觀向量(`embedding` EMA)與位置記錄(`_bbox` / `_cam`)。
**誤併的目標身份裡有 99.2% 曾經吃過誤偵的資料。**

逐鏡頭差異極大:camera_7 誤偵率 10.0%,**camera_5 50.1%、camera_6 57.8%**。

### 層 2 — 四成的時候,正確答案不在選項裡

可歸因的 2,461 次決策中 **1,012 次(41.1%)正確答案不在候選集**,
其中 99.6% 是同一個結構問題(見 §4.3):

- **54.3%** —— 那個人此刻正出現在另一台鏡頭上,而拓撲說那兩台不重疊。
  真值標註裡 camera_1 與 camera_3 共現 **116,224 次**、與 camera_2 共現 58,333 次,
  而**拓撲把 camera_1 宣告成與任何一台都不重疊**。
  `camera_1` 一台就佔這類案例的 **76.4%**。
- **38.6%** —— 那個人的 track 全部在 5 秒的 `lost_track_buffer` 內,
  chef 還掛在 `active` 沒進 `gone`,而候選路徑 (a) 只掃 `gone`。

距離上次被綁定的中位時間是 **1.42 秒**。
**這不是困難的長期重識別,是秒級的連續性斷掉。**

⚠ 拓撲判準的錯誤在於**混淆了兩個不同的問題**:

| 問題 | 該用的判準 | 目前用的 |
|---|---|---|
| 兩台能不能**同時看到**同一個人(候選集生成) | 共現與否 | ❌ 框大小 |
| 看到的框夠不夠大、能不能比對外觀(證據強度) | 框大小 | — |

9/3 的佈局實測把 camera_1 對 2/3/5 判成「門口互看」(小框寬 44~58px,
透過縫隙望進去),因此排除在 `overlapping` 之外。那個判準對**證據強度**是對的,
對**候選集生成**是錯的。

### 層 3 — 就算在選項裡,系統也沒有資訊分辨誰是誰

| 證據 | 在 CHIRLA 上的狀態 |
|---|---|
| 地面校正 `GroundPlaneLR` | **0 個單應性 → 從未生效** |
| 軌跡 `VelocityLR` | 從未生效(靠 `world_xy`) |
| 方向 `DirectionLR` | 沒有 zones → 關 |
| 轉場時間 | 42 個有向對只建了 **3 條** |
| 外觀 `AppearanceLR` | 實測 0.062 nats;網格裡是零向量 → **恰好 0** |
| 重疊 `overlap_llr` | 常數 `5.0 − ln(k)`,k 是**人數**不是身份 |

結果:**2,600 次綁定只產生 8 個相異分數,而候選集中位有 42 個。**
`identity_st.py` 的註解自己算過:要拒絕一個候選需要 `k > 29.7`,
CHIRLA 單台最多 9 人 —— **這條證據在數學上不可能拒絕任何候選**。
系統是在同分中任選一個。

### 層 4 — 每一次錯誤都讓下一次更難

59 個真人 → **826 個預測身份**。每個錯誤開出的身份都留在候選池裡(TTL 100 秒),
把候選集撐到中位 42 個,讓下一次決策更難,再產生更多錯誤。

誤併 1,433 次裡有 **906 次(63.2%)**落在 `OK` 那一列 ——
系統穩定地把這個人綁到同一個 `chef_id`,但那個 id 的多數票屬於別人。
**兩個人早就被併在一起,之後每次「正確地維持現狀」都被記成誤併。
錯誤發生在很早以前,後面只是繼承。**

## 8.2 六個修法全部落在層 3 與層 4

| 修法 | 作用的層 | 修正後 IDF1(基線 0.1512) |
|---|---|---|
| F1 margin test | L4 門檻 | 0.0393 |
| F2 同鏡頭互斥 | L3 候選排除 | 0.0679 |
| F4 CrossViewLR | L3 評分 | 0.0952 |
| F5 TransitPlaceLR | L3 評分 | 未跑(V2 未過) |

**沒有一個碰到層 0、層 1、層 2。**

而層 3 與層 4 加起來只佔可歸因失敗的 **11.7%**(L3 9.7% + L4 2.0%)。
即使把這兩層做到完美,**天花板也只有 11.7% 的改善空間**,
而層 2 一層就是 41.1%、層 1 是全部決策的 32.5%、層 0 讓問題量放大 43 倍。

這就是為什麼六輪修法全部失效,而且**那是可以事先預測的**。

具體的機制證據:P1 投了 52,259 票只改判 423 次(0.81%)——
**投票只能在候選集內重排,而正確答案有四成的時候不在裡面。**

## 8.3 更根本的:架構被跑在它被驗證過的範圍之外

M5 的七輪模擬驗證裡,**七條證據通道都是開的**。
9/1 那輪量到地面校正與軌跡把模擬誤併從 **72% 壓到 5.6%**。

在 CHIRLA 上這兩條**從未作用過**(0 個單應性),方向也是關的,
轉場時間 42 個有向對只有 3 條,外觀是零。
**七條裡有五條是關的,剩下兩條對所有候選給同一個值。**

我們一直在把系統跑在它被驗證過的條件之外,然後修它的決策程序。

## 8.4 要真的追蹤成功,必須成立的條件(依槓桿排序)

驗收門檻是**誤併 ≤ 1%**,現在 58.23%。

| # | 條件 | 打哪一層 | 現況 |
|---|---|---|---|
| 1 | **M4 不能把一個人切成 46 段** | 層 0 | 遮擋救回率 63.6%,7,779 次 removed |
| 2 | **誤偵從 32.5% 降下來** | 層 1 | 9/3 §6 已寫死處置,觸發兩輪未執行 |
| 3 | **拓撲要反映真實共現** | 層 2(54.3%) | camera_1 與六台全部沒關係 |
| 4 | **候選路徑補上 `active` 但不在畫面的 chef** | 層 2(38.6%) | 路徑 (a) 只掃 `gone` |
| 5 | **重疊路徑要有能區分身份的幾何證據** | 層 3 | 目前是常數,數學上無法拒絕 |
| 6 | **外觀證據** | 層 3(9.7%) | 0.062 nats,卡授權 |

⚠ **前五項全部是偵測、追蹤與時空,沒有一項是 Re-ID 模型。**
時空證據只能回答「**有沒有可能**是同一個人」,回答不了「**是不是**」。
一個房間裡 7 個人的時候,「有可能」不夠用 —— 所以第 6 項長期仍然必要,
但它排在第六,而且**解不了前面五層**。

## 8.5 ⚠ 結論(報告要放在結論之前)

> **以目前的資料與授權條件,在 CHIRLA 上做到誤併 ≤ 1% 不是調參能達成的。**
>
> 過去六個修法全部作用在只佔 11.7% 失敗的兩層上。
> 要有實質改善,必須從層 0(追蹤碎裂)與層 1(誤偵)開始往上修,
> **而不是繼續改決策程序**。

工作方式上的對應改變:

1. **每一個新修法都要先說它打哪一層、那一層佔多少%。** 說不出來就不要做。
2. **修法之後要重跑四層分解**,看它有沒有真的把那一層的數字降下來 ——
   只看 IDF1 會像前六輪一樣看不出為什麼沒用。
3. **由下而上修**。層 0 沒改善之前,修層 2 的效果會被 43 倍的問題量稀釋掉。
